## Abstract 

RDMA can reduce communication overhead in distributed machine learning systems, but realizing these benefits in pro-duction requires more than replacing TCP. Variable-size mes-sages, many concurrent connections, bursty incasts, and ser-vice failures place demands on software that hardware offload alone does not address. This paper reports our experience deploying ByteExpress , a software communication layer over hardware RDMA, in ByteDance’s parameter-server-based in-ference and training systems. We describe three lessons from the deployment: efficient RDMA requires buffer management that spans the application and transport; scalable communi-cation requires coordinated management of connections, re-ceive capacity, and outstanding data; and service availability requires recovery above the transport layer. Our design com-bines an RDMA-aware allocator, zero-copy message transfers, QP multiplexing, receive-credit flow control, a software send window, and RPC-assisted recovery. In a production infer-ence workload, the system reduces mean and 99th-percentile model parameter fetch latency by 35.7% and 43.7%, respec-tively, and total CPU usage by 10.69% relative to the widely deployed TCP stack. In the training workload, ByteExpress 

reduces P99 model parameter push latency by up to 74.0% relative to TCP, with no PFC pauses observed during the reported interval. 

## 1 Introduction 

Distributed inference and training underpin recommenda-tion, search, and advertising services at ByteDance, including Toutiao and TikTok. In the parameter-server architecture used by these services, workers fetch model parameters from mul-tiple servers; trainers also push updates back to those servers. These exchanges place communication on the critical path of both user-facing inference requests and iterative training. By January 2022, ByteDance’s inference and training sys-tems spanned hundreds of clusters and tens of thousands of computing nodes. Faster computation increases the pressure on this commu-nication path. GPU-based workers can generate substantial network demand [4, 21, 38], while processing data through the kernel network stack consumes CPU cycles and intro-duces copying and scheduling overhead. ## 2 Background 2.1 Inference and Training Systems 

At ByteDance, parameter-server-based systems [29] support model training and personalized ranking for recommendation, search, and advertising. Figure 1 shows the two main roles: workers and parameter servers (PSs). A worker is a ranker 

during inference and a trainer during training. Model parame-ters are partitioned into n shards, for example by hashing, and stored across n parameter servers. For online inference, an application forwards a user request to a ranker. A request may require evaluating k models. The ranker fetches the required parameters, evaluates the mod-els, and returns the ranking results. Because the parameters can span multiple shards, one user request becomes multiple concurrent sub-requests to parameter servers. Each ranker also keeps multiple user requests outstanding through asyn-chronous network I/O. Request and response sizes vary with user attributes and model structure, ranging from kilobytes to megabytes. Prior work reports similarly variable message sizes [5, 39, 50]. For training, each trainer works on a model, loads train-ing data, fetches parameters, performs forward and backward propagation, and pushes updates to parameter servers. Re-peated parameter exchanges generate incasts at both workers and servers. Throughout the paper, Fetch denotes parameter retrieval; the synthetic experiment labels the corresponding operation Pull .The measurements in this paper cover different workloads. In the training workload discussed in §6.3, mean and P99 message sizes are 20 KB and 50 KB, respectively. The allo-cator benchmark instead uses synthetic large allocations of 64 KB–1 MB and small allocations of 16 B–16 KB (§5.2). The production inference evaluation uses 300 parameter servers and 124 rankers; the training evaluation uses 124 parameter servers and 346 trainers (§8). These examples characterize the evaluated cases, not a single distribution shared by all services. 

## 2.2 RDMA: A Primer 

Remote Direct Memory Access (RDMA) provides low-latency, high-throughput communication using specialized NICs. RNICs offload transport processing and expose opera-tions to user-space software, avoiding kernel-network-stack overhead on the data path. Software still allocates buffers, posts operations, and processes completions; RDMA does not eliminate application-side CPU work. A queue pair (QP) is a communication endpoint with a send queue (SQ) and a receive queue (RQ). Applications access RNIC functionality through the verbs interface, which sup-ports resource creation, work-request submission, and com-pletion polling. Completed operations are reported through a completion queue (CQ). Two-sided messaging verbs, SEND and RECV , require par-ticipation from both endpoints: the receiver posts a receive buffer before the incoming send can be completed. One-sided memory verbs include WRITE , READ , and atomic operations; RDX proposes extending RDMA beyond memory access to remote code execution [17]. They access registered remote memory without requiring the remote CPU to execute a match-ing operation for each transfer. ## 3 Deployment Requirements 

Our goal is to improve communication performance while retaining the scalability and availability expected of produc-tion inference and training services. The following workload properties determine our design choices. 

Variable messages and buffer lifetimes. Inference and training exchange messages whose sizes are not always known before a request is processed. Application threads may also retain or transfer ownership of a received buffer while computing a result. A fixed receive-buffer layout can complicate zero-copy integration in this setting. Registering a new buffer for every message avoids that layout constraint but adds registration overhead and increases the number of memory regions. We therefore need dynamic allocation from reusable, registered memory (§5.2). 

Large transfers favor RC, but RC connections must be managed. UD-based designs such as FaSST and eRPC [22, 25] demonstrate the benefits of connectionless communica-tion, particularly for small messages. Our workload also in-cludes messages much larger than the MTU. Sending them over UD requires software fragmentation, reassembly, and reliability. Section 5.1 compares RC and UD throughput un-der several link-rate and MTU configurations. We choose RC for its hardware support for reliable, large-message transfers, then multiplex logical connections to limit QP-state pressure (§6.1). This is a choice for our workload and deployment, not a general argument against UD. 

Receive capacity and fabric congestion are separate con-straints. A sender can exhaust posted receive requests even when the network is uncongested. Conversely, a receiver with available buffers can still be reached through a congested net-work. We address the first problem with credits for operations that consume receive requests (§5.4). We address the second by limiting outstanding bytes per engine, in addition to the existing DCQCN and PFC mechanisms (§6.3). Keeping these controls separate makes their roles explicit: receive credits prevent receiver-not-ready (RNR) events; the send window limits the amount of data injected during concurrent transfers. 

Incast makes tail behavior a scaling concern. Many work-ers can contact the same parameter server, and responses from many servers can converge on a worker. Service recovery requires application context. An RNIC can provide reliable delivery on a functioning connection, but it cannot select another service replica or decide how to retry a failed RPC. Fan-out operations are particularly sensitive to slow or failed sub-requests. We therefore retain Archon’s RPC abstraction and extend its existing availability mechanisms to cover RDMA connection failures and fallback to TCP (§7).

## 5 Building a High-Performance Communication Engine 

This section describes the data path, from transport selection and buffer allocation to message transfer and work-request processing. The key requirement is to preserve the benefits of hardware RDMA while supporting variable-size messages and application-controlled buffer lifetimes. 

## 5.1 Choosing RC for Large-Message IO 

BE uses RC to retain hardware support for reliable, large-message transfers. UD avoids maintaining a dedicated trans-port connection to each peer, but its MTU-sized messages re-quire additional software processing for larger payloads. The measurements in Table 2 illustrate how this tradeoff changes with link rate and MTU. At 25 Gbps with a 1,024-byte MTU, RC and UD both ap-proach the link rate. At 100 Gbps with the same MTU, RC reaches 92.26 Gbps while UD reaches 48.29 Gbps; increasing the MTU to 4,096 bytes brings both close to line rate. At 200 Gbps with a 4,096-byte MTU, RC reaches 191.36 Gbps and UD reaches 114.70 Gbps. Thus, packet-processing rate can constrain throughput as link bandwidth grows, even though UD performs well in other configurations. These mea-surements support our choice of RC for the evaluated work-load, rather than a general claim that UD is always bandwidth-limited. Section 6.1 explains how we manage the connection-state cost of that choice. 

## 5.2 RDMA Memory Management 

To support zero-copy transfers of large, variable-size mes-sages, we need dynamic allocation of registered memory. Ideally, allocating and freeing RDMA buffers should be as straightforward as using a general-purpose allocator such as 

jemalloc [8] or tcmalloc [28]. We implement this interface by extending an existing allocator with memory registration and memory-region tracking.

Registration cost and pool reuse. Registration remains necessary when the allocator acquires a new block, and dereg-istration is required when it releases one. Their cost is amor-tized across allocations from that block. Once the registered pool reaches a stable size, subsequent allocation and deal-location operations can be served from cached blocks with-out further registration. ## 5.4 RDMA Engine 

Each BE engine owns one QP and its associated state, includ-ing a work-request chain and receive buffers (Figure 7). It is the lowest software layer: it posts verbs operations and processes completions. Above it, sockets represent logical connections and a scheduler coordinates their I/O. We use 

engine when referring to this software state and QP when referring to the RDMA resource. Section 6.1 describes socket multiplexing and scheduling. 

5.4.1 Work Request I/O 

The engine uses preallocated resources and batching to reduce data-path overhead. Its send-side work requests form a circu-lar chain whose length equals the QP send-queue depth. Track-ing occupied entries avoids dynamic work-request allocation and prevents the engine from posting more requests than the send queue can hold. We use relatively shallow queues, for example a depth of 32, provided that they allow enough outstanding work to sustain the target throughput. 

Work-request chain. The chain has three contiguous seg-ments: in flight , pending , and free . In-flight requests have been posted to the RNIC and await completion; processing their completions frees the corresponding slots. Pending re-quests have been prepared but not posted. The engine submits them together with one ibv_post_send() call, using door-bell batching [24]. Only the last request in a batch requests a completion notification, reducing completion-processing overhead. When free slots are available, the scheduler polls sockets for work; each selected socket prepares a request of at most one fragment. The engine tracks the segment boundaries in the circular chain. 

5.4.2 Flow Control 

BE uses SEND /RECV for control messages and small payloads. A SEND consumes a posted receive request at the peer; if none is available, the peer reports receiver not ready (RNR), causing retries and potentially a transport error. WRITE_WITH_IMM 

also consumes a receive request. We therefore track receive capacity explicitly. This flow control protects endpoint receive queues; it is separate from the network congestion control in §6.3. 

Receive-credit flow control. Inspired by receiver-driven transport [37], each sender maintains credits for available receive requests at its peer. The endpoints exchange the ini-tial credit count during connection setup. Posting a SEND or 

WRITE_WITH_IMM consumes one credit; ordinary WRITE oper-ations do not consume credits because they do not use receive requests. The sender waits when it lacks the required credit. The receiver replenishes capacity in batches. After con-suming k receive requests, it posts k replacements with one 

ibv_post_recv() call and sends a credit update to the peer. Batching reduces the frequency of posting calls and credit messages. We use k = d/2, where d is the receive-queue depth. Choosing k < d leaves capacity available while an update is in transit, although a sufficiently delayed update can still stall the sender. This scheme targets RNR avoidance with dedicated receive queues. The optional shared-receive-queue configuration trades this per-peer accounting for shared buffer capacity (§6.2.2).

## 6 Scaling Connections & Concurrent PS Ops 

Scaling the communication path requires managing both con-nection state and aggregate traffic. This section describes QP multiplexing, thread-aware resource management, and a software send window for incast workloads. 

## 6.1 QP Management 

RNICs have limited cache space for QP context. When the active working set exceeds that capacity, the NIC must fetch missing context from host memory through DMA, increasing overhead. BE reduces this pressure by multiplexing logical connections onto QPs. Archon keeps multiple requests outstanding through RPC channels, each with its own socket. With TCP, each socket has a separate transport connection. With BE , sockets directed to the same remote address can share one engine (§5.4). 

Multiplexing sockets onto QPs. BE maintains a connec-tion table that maps remote addresses to engines. When an application calls connect() , BE attaches the socket to an existing engine for that address, if available. Otherwise, it cre-ates an engine and reports connection success asynchronously after setup completes. This allows one QP to serve multiple logical connections to each remote address. Sharing an engine introduces scheduling head-of-line (HoL) blocking: a large message from one socket can de-lay smaller messages from another. BE fragments messages so that the scheduler can interleave their work requests. Frag-ment size trades scheduling granularity against per-request overhead. Figure 10 shows that approximately 2 KB frag-ments can saturate the tested 25 Gbps link with one QP, whereas fragments larger than 8 KB are needed for near-line-rate throughput on the tested 100 Gbps link. Each socket queues outgoing messages. When selected by the scheduler, it prepares a work request for at most one fragment by supplying that fragment’s address and length; no payload copy is required. ## 6.2 Avoiding Contention in Multithreaded I/O 

6.2.1 Thread Ownership and Provider Resources 

Figure 12 shows the mapping of engines to I/O threads. Each engine is bound to one thread, so operations on its data struc-tures do not require locks between I/O threads. A thread can manage many engines. We assign engines in round-robin order, which is sufficient for the evaluated workload. 

Contention inside the RDMA provider. Single-thread ownership of each engine did not eliminate all contention. Thread-aware resource allocation. We use a separate thread domain (TD) for each I/O thread to communicate the ownership arrangement to the verbs provider. Thread domains permit provider optimizations for resources accessed by a single thread [44]. This requires the application to respect that ownership discipline. Separating threads into independent protection domains (PDs) would complicate cross-thread use of registered memory; instead, our configuration retains a common protection domain while associating resources with their respective thread domains. 

6.2.2 Sharing Queues Within an I/O Thread 

Single-thread ownership also lets engines share selected re-sources without introducing locks between I/O threads. Ta-ble 3 summarizes the allocation: QPs remain associated with remote addresses, while CQs and TDs are allocated per thread and registered memory belongs to a common PD. This re-duces per-QP overhead, although QP-specific state still grows with connection count. 

Completion queues. Each I/O thread maintains one CQ for the send and receive queues of its assigned QPs. It re-trieves completion queue entries (CQEs) in batches with 

ibv_poll_cq() and uses each entry’s QP number to identify the corresponding engine. This extends the engine’s batched completion processing (§5.4) across connections and avoids polling a separate CQ for every QP. 

Shared receive queues. Dedicated RQs reserve receive buffers for individual peers. As an alternative, BE can create one shared receive queue (SRQ) per I/O thread, allowing all engines assigned to that thread to draw from a common buffer pool instead of using dedicated RQs. This improves buffer utilization but changes the flow-control contract. The credit scheme in §5.4.2 tracks per-peer receive capacity and does not directly apply to a shared pool. Engines can be created and destroyed dynamically, so precise allocation of shared capacity requires additional coordination. In SRQ mode, we use larger queues and configure RNR timeouts and retry counts to reduce the impact of receive-buffer exhaustion. This mitigates RNR events but does not enforce the per-peer receive-capacity bound of the dedicated-queue credit scheme. The choice is therefore between explicit per-peer capacity accounting and more flexible sharing of receive buffers. 

## 6.3 Application-Level Congestion Control 

Incast places a different limit on scale: many individually efficient senders can collectively overwhelm a receiver’s net-work path. We supplement hardware congestion control with a software bound on outstanding bytes. 

Iterative incasts in training. Both inference and training exhibit fan-in and fan-out, but repeated parameter synchro-nization in training can sustain concurrent transfers to the same destinations. In the training workload considered here, mean and P99 message sizes are 20 KB and 50 KB. Con-current Fetch /Push requests can produce substantial incast congestion and frequent received PFC pause frames. Our objective is to sustain concurrent transfers with low tail latency while reducing PFC activity. Absence of PFC pauses does not imply absence of congestion; it indicates that the measured workload did not trigger that protection mechanism. We use request P99 latency as a proxy for communication stalls, rather than as a direct measure of end-to-end training throughput. Prior work has also identified congestion challenges in RDMA networks [10, 22, 51]. In our deployment, DCQCN alone did not react quickly enough to the observed incasts. Its rate-control dynamics motivate additional control over how much data software makes outstanding. ## 7 Maintaining Service Availability 7.1 Transport Reliability & Service Recovery 

Online inference must return results within service latency tar-gets, while training must make progress despite failures. Fan-out makes both sensitive to slow sub-requests: a single stalled destination can delay a larger operation. RC handles transport-level delivery on a functioning connection, but recovery from node failures, persistent path failures, and unavailable replicas requires decisions above the transport layer. Network monitoring can help locate faults [1,12], and prior deployments combine network and application mechanisms for recovery [9]. We follow the same general principle: retain service-level recovery in Archon and add the RDMA-specific monitoring and fallback mechanisms needed by our deploy-ment. 

## 7.2 Deployment and Recovery Mechanisms 

Archon supported production inference and training before the RDMA deployment, including RPC-level availability poli-cies and load balancing. Integrating BE preserves those poli-cies. Before deployment, we test RDMA-equipped machines with Collie [26] to identify performance anomalies. We also use a watchdog-based approach to contain PFC storms [11]. 

Replication across failure domains. Rankers and param-eter servers are deployed across multiple geographic data centers. Within a data center, parameter-server replicas are placed in different mini-pods, each replica containing the n

shards described in §2.1. The network between mini-pods within a big-pod supports the lossless RDMA configuration. Replication provides alternative service destinations when a node or path fails; integrated network monitoring helps locate the underlying problem. 

Connection monitoring. BE detects QP errors through completion polling and verbs return values. It also sends keepalive messages to detect failures such as a remote kernel panic or power loss. Each engine periodically sends its peer a monotonically increasing sequence number. If the peer’s sequence number does not advance before the keepalive time-out, the engine enters an error state, notifies the upper layer, and reclaims connection resources. The send interval and failure-detection timeout must accommodate normal schedul-ing delays. 

RPC-assisted recovery. Archon uses separate connection and request timeouts, chosen for the cluster topology and service requirements. Example thresholds are Tc = 10 ms for connections and Tr = 40 ms for requests. A timed-out request may be retried probabilistically to tolerate transient failures. These transport and request timeouts serve different purposes from the keepalive mechanism. Recovery proceeds through several options. First, the sys-tem attempts to change the connection path using the RNIC’s port-affinity support [41]; the reported deployment uses MLNX OFED 5.0 or later with compatible firmware. If recon-necting does not resolve the failure, Archon selects a nearby replica in another mini-pod. If RDMA communication re-mains unavailable, it falls back to TCP, following the gen-eral approach used in prior RDMA deployments [9]. ## 9 Deployment Lessons in Production 

Our experience deploying RDMA in production ML inference and training systems yielded several practical lessons. 

Integrate RDMA buffer ownership across layers. The practical value of bemalloc is the buffer-ownership contract it enables across the application and transport. Registered memory becomes useful to applications when allocation, seri-alization, transfer, and reclamation follow a consistent lifetime model. Integrating this contract beneath Archon’s RPC inter-face allows applications to benefit from zero-copy transfers while retaining their existing communication abstraction. 10 Figure 16: PS performance in a production recommendation inference workload: mean and P99 for TCP and RDMA in microseconds, sampled at one-minute intervals for the busiest rankers. 

Control receiver capacity and outstanding traffic sepa-rately. Receive credits protect posted receive capacity, while the software send window bounds outstanding data above DCQCN and PFC. In the production training workload, hardware congestion control alone left P99 latency above the deployed TCP baseline. Adding the software window reduced P99 push latency to 268 ms, with no PFC pauses observed during the measurement interval (Table 7). The operational lesson is to assign each control a specific resource to protect. 

Align RDMA resource sharing with IO thread ownership. 

Assigning each engine to one I/O thread removed contention in our own data structures, but provider-side spin locks still limited message rate as QP counts grew. Thread domains aligned provider resources with application ownership, while per-thread queue sharing reduced resource overhead (§6.2). Effective scaling therefore required inspecting contention across the application–provider boundary. 

Keep RDMA transport reliability close to service policy. 

Archon retained responsibility for request timeouts, replica selection, and TCP fallback, while BE supplied connection-error and keepalive signals (§7). This division lets recovery use service context, including replica placement across failure domains and the exclusion of repeatedly failing destinations. Preserving these policies was a central part of integrating RDMA into an existing production service. 

## 10 Related Work 

RDMA systems and machine learning. RDMA has been used in key-value stores [23, 31], distributed transac-tions [7, 49], distributed storage systems [13, 14], cloud se-curity system [32], disaggregation [19, 34, 46], and RPC [22, 47]. EFLOPS [5] studies RDMA-enabled distributed train-ing through system and algorithm co-design, while Xue et al. [50] integrate RDMA into distributed machine learning. Rather, our focus is the operational RDMA co-design across registered-memory allocation, message transport, resource sharing, and RPC-level recovery for PS-based inference and training. 

Connection scaling. QP context and resource sharing are established RDMA design concerns [24, 36]. SkyRDMA [15] explores offloaded RDMA connection sharing policies at the hardware level in AI clouds. Prior work also explores software-defined scheduling of RNIC resources [18] and GPU fabrics [3]. Dynamically Connected transport provides an-other approach: an initiator can communicate with multiple targets without a dedicated RC connection to each [40]. BE 

instead multiplexes logical sockets over RC QPs and uses thread domains to align provider resources with I/O-thread ownership. 

Congestion control. DCQCN [51], TIMELY [35], Swift [27], and HPCC [30] explore different congestion sig-nals and transport-control designs. Instead, our software win-dow provides application-level control over outstanding RC traffic, layered above the existing DCQCN configuration and complementary to prior studies. 

## 11 Conclusion 

Deploying RDMA in production inference and training sys-tems requires coordinating application interfaces, memory ownership, transport resources, and service recovery. Byte-Express combines an RDMA-aware allocator and zero-copy transfers with QP multiplexing, thread-aware resource man-agement, receive credits, and a software send window. Archon retains the RPC-level context needed for retries, replica se-lection, and TCP fallback. The reported deployments demon-strate lower parameter-fetch latency and CPU usage relative to the deployed TCP baseline, while exposing limits that hard-ware offload alone does not resolve. The broader lesson is to assign each layer a clear responsibility and evaluate the result-ing communication path under the concurrency and failure patterns of the target workload.
