## Abstract 

Datacenter congestion control (CC) and load balancing (LB) evolve rapidly as workload demands change, but deployment depends on RDMA hardware and transport interfaces. Emerg-ing programmable RDMA engines tie policy code to vendor APIs. Operators must therefore port each policy for every platform they deploy. We address this with PCM, a program-ming model that separates portable congestion management from platform integration on datacenter NICs. Developers write event-driven handlers that they can debug in simulation and reuse on real hardware. PCM exposes flow telemetry as signals and uses triggers to support per-event reactions and coarser responses to accumulated feedback. Vendors provide optimized backends that map signals and output con-trols to native NIC mechanisms with defined feedback and control semantics. We demonstrate PCM’s expressivity by implementing eleven well-known datacenter CC and LB al-gorithms. We deploy PCM across four distinct datapaths: an Ultra Ethernet simulator, CPU-based UCCL, and on-NIC offloads on NVIDIA ConnectX-8 and Microsoft 1P. On CX-8, PCM-Swift achieves processing capacity equivalent to one reaction per three 4 KiB packets at 800 Gbit/s, using one-fifth of the NIC’s hardware threads. In UCCL, it matches native Swift’s 1.56 Tbit/s goodput with 64 KiB chunk-level control. PCM’s design informed ongoing Ultra Ethernet work toward a portable congestion management interface. 

## 1 Introduction 

Datacenter operators seek workload-specific congestion con-trol and load balancing [1, 7, 19, 25, 26, 31, 42, 46] to meet rapidly evolving workload requirements [14, 15, 17, 29, 30, 32, 34, 40, 44]. Hardwiring these policies into the RDMA transport ASIC forces a multi-year cycle to tape out, test, and deploy new silicon [43]. This cycle cannot keep pace with changing AI models, topologies, or congestion signals. Emerging programmable RDMA engines shorten the cy-cle by accepting new algorithms after deployment, but their execution models and APIs tie policy code to a particular architecture, transport, or vendor [4, 23, 35, 39]. Programmable Congestion Management (PCM) is an open-source programming model for datacenter NIC policies. It separates policy development from platform integration through portable control objects and performance-optimized accessors. Developers express algorithms as event-driven 

handlers over signals, triggers, controls, and private state. Platform backends generate shells that map these objects to arXiv:2610.13130v1 [cs.NI] 9 Oct 2026 native state and CC/LB hooks, preserving handler source while allowing platform-specific optimization. This enables 

source compatibility : developers reuse unchanged handler code across supported platforms by generating a shell for each target. Deployment parameters and behavioral valida-tion remain target-specific. Handler performance is as important as portability. At 1.5 GHz and 0.5 instructions per cycle, a core can execute only about 15 instructions per 4 KiB packet at 1.6 Tbit/s. Set-ting up a single function call can exhaust this budget. PCM closes this gap at three levels. First, shell generators compile NIC state accessors into native loads and stores to minimize abstraction overhead. Second, handlers for independent flows map transparently to parallel, energy-efficient NIC cores, in-creasing aggregate capacity. Third, hardware-aware signal accumulation preserves counts and feedback summaries while decoupling the execution of instruction-heavy or resource-limited handlers from event arrival rates. Together, these mechanisms let portable handlers approach bare-metal perfor-mance, react at nearly per-packet granularity when capacity permits, and consume accumulated feedback when policies tolerate coarser reactions. To demonstrate PCM’s expressivity, we implement eleven state-of-the-art datacenter CC and LB algorithms, most in fewer than 100 lines of C. We implement shell generators for four platforms. UET-htsim enables correctness checks and parameter tuning before deployment [12]. Integrating PCM into UCCL tests portability to a CPU-based software RDMA transport [45]. We support PCM offload on NVIDIA CX-8 and Microsoft 1P, two NIC architectures with different hardware RDMA transports. Our evaluation answers four questions: What does the ab-straction cost? What does policy reuse require? How does execution scale? What reaction rates can each platform sus-tain? Matched native baselines and targeted experiments re-veal how arithmetic, feedback granularity, worker placement, and flow-state footprint shape the performance and behavior of portable PCM policies. 

We make the following contributions: 

1. Design requirements: We derive expressivity, portability, and performance requirements from workload needs and existing mechanisms. 2. A unified, efficient programming model: We define hardware-friendly abstractions for portable NIC policies with per-event and coarser reactions. 3. Multi-platform validation: We demonstrate eleven poli-cies, four platform integrations, and full CC offload. 4. Ultra Ethernet standardization impact: Our work in-formed ongoing standardization of programmable conges-tion management.

## 3 Related Work 

Supporting workload-specific congestion management re-quires both programmable policies and reusable platform integration. Table 1 compares existing mechanisms for NIC congestion management. They bind policy code to hardware, interfaces, or host runtimes. PCM addresses this gap through CC/LB source portability across substrates, defined signal and control semantics, and native execution on embedded NIC cores. This combination extends policy reuse from simulation to NIC deployment. 

Hardware and transport dependencies: HotCocoa provides programmable hardware abstractions for CC logic in Ver-ilog [3]. Tonic extends this approach to a 100 Gbit/s FPGA design, with Verilog templates for incoming-packet logic and periodic CC updates [4]. It processes relevant events every cycle, but policy changes require synthesis, timing closure, and target-specific verification. AMD Pensando and Broad-com Thor Ultra similarly tie P4-like pipeline code to vendor compilers, stages, metadata, and actions. NVIDIA DOCA PCC compiles C callbacks for the Con-nectX DPA, with ABI-specific flow contexts, events, algo-rithm attributes, and results [35, 43]. It can coalesce events into aggregate counters. The DOCA PCC interface exposes RoCEv2 and RDMA engine control events and RTT probes, and provides nanosecond RTTs and fixed-point arithmetic helpers. Google’s Falcon transport specifies an asynchronous en-gine that consumes ACK-, NACK-, and retransmission-triggered events and returns CC and path-selection con-trols [39]. The Falcon datapath filters control events accord-ing to queue occupancy, elapsed time, and acknowledged volume, while accumulating ACK counts between engine updates. These NICs expose native transport event formats, state layouts, and controls to policy code. 

Programming language and runtime dependencies: Linux TCP loads telemetry-driven CC handlers as eBPF bytecode without rebuilding the kernel. Their C code depends on kernel callbacks (tcp_congestion_ops), helpers, and socket state, pre-venting offload to RDMA NICs [20]. Presto’s Tofino 2 RMT datapath implements TCP, aggregates acknowledged/ECN-marked bytes and duplicate ACKs, and enforces rates [38]. Its off-path C++ control plane runs DCTCP or Timely and updates rate tables, with configured minimum intervals of 50 μs between polls and 80 μs between datapath-generated credit messages. These policies retain dependencies on the P4 datapath and C++ control plane. UCCL implements GPU transport pacing, loss recovery, CC, and path selection over multi-packet chunks striped across RDMA queue pairs using Verbs UC Write [45]. Portability across Verbs providers still leaves this logic tied to UCCL’s classes and path APIs. All three systems require interface changes for deployment on other substrates. For example, Presto’s and UCCL’s C++ poli-cies cannot compile with the DOCA PCC C11 compiler [35]. 

Host control plane delay: CCP preserves CC source across different host datapaths and protocols, including Linux TCP, QUIC, and mTCP [33]. It extends event coalescing with pro-grammable filters and reporting rules. Policies can request per-event reports when the control-plane agent keeps pace or aggregate measurements before reporting. CCP interprets these rules as DSL programs on each ACK or timeout to ac-cumulate measurements, select reports, and update controls. Portus, CCP’s Rust runtime, runs the CC algorithm in a sepa-rate user-space process. It delivers reports to that algorithm and returns its control updates through POSIX IPC. On our Intel Xeon Gold 6140, CCP’s NewReno cycle takes 10 μs. A single Linux kernel IPC call takes about 3 μs on this system, the runtime-interpreted DSL takes 350 ns, and NewReno cal-culation takes 300 ns. At 1.6 Tbit/s, a 4 KiB packet arrives every 20 ns. CCP’s filters and control plane round trip exceed this deadline by orders of magnitude. While some sender-side CC algorithms tolerate coarse control, others, such as MP-RDMA, target nearly per-packet reactions [31]. ## 4 Design Requirements 

The use cases and NIC mechanisms discussed in Sections 2 and 3 motivate three requirements for PCM. 

Expressivity: A common programming model needs to ex-press sender-side CC, receiver-side credit control, and stateful LB to accommodate diverse workload requirements. 

Portability: Maintaining separate simulator and NIC imple-mentations requires repeated integration work and creates opportunities for bugs. Policy reuse therefore requires sepa-rating handler logic from native APIs, state layouts, measure-ment units, and arithmetic implementations. We target source compatibility : unchanged policy code across supported back-ends, with deployment-specific parameters and numerical precision. Feedback granularity, arithmetic, scheduling, and native and approximated controls can still affect behavior, so each deployment requires behavioral validation . A backend must reject a handler if the platform cannot provide a required signal or enforce a required control. 

Performance: Terabit rates demand low execution overhead and sufficient aggregate processing capacity. Portable han-dlers should approach native execution performance and scale across independent flows. Platforms also expose feedback at different granularities: DOCA PCC and Falcon can aggregate feedback before invoking policy code, while UCCL delivers ACKs for multi-packet chunks. PCM should exploit native execution and feedback mechanisms to minimize overhead and increase processing capacity. It should support per-event execution when the platform can sustain it and accumulated feedback when deployment-specific validation shows that the policy tolerates coarser reactions. Section 7 examines these requirements through algorithm coverage, policy reuse across transports, and measurements of execution cost, goodput, and scaling. 

## 5 PCM Programming Model 

We introduce a programming model to express congestion management algorithms as portable, event-driven handlers .A PCM handler is a stateful function that operates on per-flow state independently of hardware details. Each handler context belongs to one flow. Developers may compose modular logic by associating a flow with multiple handlers whose controls do not overlap. For example, separate handlers can implement load balancing and congestion control. Matching flow events to a handler context is outside PCM’s scope. It depends on the NIC transport, traffic-steering engine, and transport addressing. 

## 5.1 Unified Datapath Abstractions 

Figure 3 shows how PCM separates congestion management policy from platform-specific event management and control enforcement. A handler uses get and set accessors to read signals, update controls, and maintain private state. These accessors provide a safe API that hides each object’s internal representation. 

Controls: A control specifies a transport knob, such as a win-dow, rate, path entropy, or cumulative credit. After execution, the handler returns its controls to the transport. 

Signals: A signal exposes datapath telemetry or live state. Examples include counts of ACKs, NACKs, RTOs, and ECN marks, as well as RTT, elapsed time, queue backlog, and path identity. Each signal selects an accumulator: SUM for counts, 

MIN /MAX for extrema, or LAST for the newest value. Accu-mulator storage is independent of event count, and several named accumulators can share one telemetry source. 

Triggers: PCM invokes handlers through a triggering mecha-nism driven by accumulated flow events. A trigger uses a particular signal value to determine when a handler should run. The backend combines all fired triggers into one mask. The handler reads the mask to select its branches. The generator emits constant object identifiers, the snapshot layout, and the required accumulation, trigger, snapshot, and commit operations. The compiler folds accessors into native loads and stores, eliminating runtime lookup and mask conversion. Each trigger evaluates a single-instruction condition against the accumulated value and a static threshold . The compari-son supports several modes. RAW compares the accumulated value with the threshold. DELTA compares the change since that trigger’s last satisfied check. MAGNITUDE compares the absolute change from the same baseline. For example, an ACK counter with DELTA >= 1 permits per-packet reactions when the shell keeps pace. If the control law permits, a higher threshold allows less frequent reactions. 

Variables and constants: Variables hold persistent private state, including signed and unsigned scalars and fixed-size arrays. Developers can choose floating-point or fixed-point representations for fractional variables at compile time. Con-stants define state that remains immutable throughout a flow, such as base RTT and MTU. The compiler resolves them at compile time to optimize calculations and eliminate unneces-sary loads. 

## 5.2 Handler Compilation 

The specification lists all objects used by the handler and their properties. The C source and specification form a han-dler package. Figure 4 shows how a compiler combines this package with a platform backend API to produce a shell .

Object generation: The shell translates datapath events to signals and maps controls to native mechanisms. For each specified object, the compiler emits logic that implements its semantics. Generated code for HIGH_RTT in the example in Figure 4 branches on the native RTT-probe event and checks whether the converted RTT exceeds 150 PCM ticks (15 μs). 

Object representation: Shells can normalize or approximate exposed feedback and controls. The example in Figure 4 converts the probe from 10 ns platform ticks to 100 ns PCM ticks. Some handlers evaluated in Section 7 use byte counts. On ConnectX, the backend API delivers only cumulative ACK counts. The shell estimates acknowledged bytes by multiplying that count by the configured MTU. However, shells cannot recover unavailable information or capabilities. The compiler checks interface support before deployment. For example, our ConnectX backend rejects LB handlers because its backend interface lacks path selection. 

Source compatibility: Successful shell generation from the handler package establishes source compatibility . Develop-ers validate handler behavior in simulation and deployment with the available signals, constants, and numerical precision. Vendors validate event accounting, units, state placement, scheduling, and native control mappings. 

Compile-time optimizations: Separating the handler from its specification enables compile-time optimizations (Figure 4). We exploit these opportunities in all our shell compilers (Sec-tion 6). The compiler can use the specification to set up a static memory layout for handler objects, fold object accesses into native loads and stores, and map accumulator updates to hardware primitives, such as ConnectX’s event coalescing or atomic instructions. On both AArch64 and RISC-V, each signal accumulation takes one (SUM, LAST) or two (MIN, MAX) instructions with operands in registers. 

## 5.3 Handler Execution Modes 

PCM defines two execution modes relative to flow events. In synchronous mode, the shell completes the execution cycle in Figure 3A on the flow’s event path. Signal updates and execution do not overlap, so the shell can use non-atomic context storage. In asynchronous mode, a separate control plane evaluates triggers and runs handlers independently of datapath progress. The shell exchanges signals and controls between the data and control planes. Our asynchronous CPU shell connects the datapath API to accumulators and controls through CPU atom-ics. On ConnectX, the closed-source PCC runtime exchanges events and control results between the RDMA datapath and the DOCA PCC flow context. Snapshots: Snapshots preserve get /set signal semantics across both execution modes (Figure 4). Datapath updates cannot change the captured values during execution. Handler writes remain local until commit. Some transports may update multiple signals per event, such as an ACK carrying a cumulative acknowledged count and an RTT sample. Asynchronous shells may need to up-date individual signal accumulators one by one, as our CPU shell does through atomics. Locking all accumulators while copying a snapshot could stall both planes. To avoid these stalls, PCM permits relaxed snapshot delivery. Each signal preserves accumulation order, but the handler may read feed-back from different update epochs. For general bounded skew, we propose letting policies specify a maximum and shells tag updates with sequence numbers to discard snapshots that ex-ceed it. Our evaluated asynchronous CPU shell implements relaxed and zero-skew snapshots.

## 6.1 CPU Reference Shell 

Our reference CPU shell is implemented in C++ and supports integration with UET-htsim and UCCL. The handler specification is represented as a type tuple that instantiates a variadic template shell class. The instantiated shell class specializes a shell for a given handler. Fold ex-pressions and if constexpr omit redundant checks. The shell class can be specialized with signal storage for syn-chronous or asynchronous execution. Synchronous storage uses ordinary C++ datatypes and operations. Asynchronous storage uses an atomic fetch-add for SUM , a store for LAST ,and compare-and-exchange for MIN /MAX .We compile the shell into a separate shared object. Data-paths load algorithms and use the shell factory to create per-flow shell instances. A virtual API flushes a datapath-input structure into signal accumulators. A mask selects feedback, byte counts, RTT, queue state, and path information to selec-tively apply feedback to the signal accumulators. Separate structure fields return window, rate, and entropy controls. We compile handlers with Clang and LLVM [27] and also pro-vide optional custom passes to check handler safety, including detecting potentially unbounded execution paths. 

UET-htsim: Simulator hooks map the simulator clock, ACK, NACK, ECN, LB and credit pull request events to the shell input structure. Synchronous mode applies controls before window enforcement, path selection or credit generation. We also extend the simulator’s NIC scheduler to model an asyn-chronous control engine that executes handlers in a separate event chain. 

UCCL: UCCL distributes flows across CPU threads that frag-ment buffers into multi-MTU chunks and provide reliable delivery over unreliable Verbs RDMA Writes. UCCL de-faults to a software CC module that runs synchronously on the chunk-processing path. We connect it to our synchronous CPU shell. Synchronous PCM maps ACK, NACK, and RTT feedback and applies the resulting window inside the transport callback. We also extend UCCL to support an asynchronous CC plane that serves all datapath threads from an independent thread. The two planes communicate through the CPU refer-ence shell’s atomic storage. The PCM worker scans contexts and checks triggers. It publishes window updates on separate atomic cache lines for independent datapath reads. 

## 6.2 ConnectX DOCA PCC Shell 

The ConnectX-8 shell offloads PCM to Datapath Accelerator (DPA) cores through the DOCA PCC API. The DPA has 16 cores, each with 16 hardware threads. The shell uses DOCA PCC callbacks that run asynchronously relative to the hardware RoCEv2 engine [35]. Each per-flow callback runs the shell and returns a rate and RTT-probe requests. The shell generator uses the handler’s specification to emit DOCA PCC glue code that is compiled using the DPA’s DPACC compiler. This code wraps native SUM-based coalescing for TX-burst, ACK, NACK, and CNP events and handles RTT probes. 

Per-flow state: DOCA PCC provides 48 application-context bytes per flow (RC QP). This space holds a handler context pool index, output rate, outstanding bytes, probe state, RTT, and debugging metadata. The first event atomically reserves a pool slot and initializes the flow’s generated handler state. 

DPA arithmetic: The DPA lacks floating-point hardware and supports only a few mathematical intrinsics in the fixed-point Q16.16 format. To support Swift and CUBIC, we implement arithmetic, comparison, root, reciprocal, and inverse-square-root macros. These macros emulate fixed-point arithmetic in software using the open-source fixedptc library. The library supports 32- or 64-bit formats chosen at compile time. Our production implementation will replace these macros with a custom shell compiler pass that uses C arithmetic operators and a subset of the math.h API. 

Native controls: The only datapath control knob that DOCA PCC supports is QP rate. The shell exposes rate control to PCM handlers in bits per 100 ns tick. It maps this value to ConnectX’s native Q20 integer encoding of the link-rate fraction. For functional testing of purely window-based al-gorithms, the shell adapts Swift’s native pacing method to approximate rate as CW ND /EWMA (RTT ), using an exponen-tially weighted moving average of RTT [12, 26, 45]. Native window support in future ConnectX generations would let the shell select the window output.

## 7.3 PCM-Swift Case Study 

We follow the PCM workflow in Figure 1: validate Swift’s numerical representation in UET-htsim, optimize its com-putation, and test its scheduling tolerance. We then deploy the same C policy source on three live platforms, changing deployment constants such as MTU and BDP in the specifi-cation. Platform shells provide target-specific arithmetic and native control mappings. We validate the resulting deploy-ments through goodput, control behavior, and fairness. We use Swift for end-to-end behavioral validation for two reasons. First, it performs one of the most complex compu-tations among the supported algorithms. Its target-RTT and estimated-RTT computations involve division and square-root operations and together account for ≈ 90% of the per-ACK processing cost. This makes Swift a demanding test of arith-metic performance on our NIC offloading platforms. Second, Swift requires only ACK and RTT feedback, matching the signals available in our Spectrum-5 fabric, and natively sup-ports pacing rate control, the only datapath control available through ConnectX’s DOCA PCC. 

Step 1: Correctness testing. The CX-8 DPA is one of our of-fload targets. It lacks floating-point hardware, so we test fixed-point alternatives. The DPA-native 32-bit Q16.16 fixed-point data type has 16 integer and 16 fractional bits. In Figure 6a, we establish a stable fixed-point representation that preserves the tested numerical behavior. Swift’s CWND output with Q16.16 is distorted. The Q16.16 variant’s CWND oscillates between its one-packet initial window and approximately 32 KiB. This variant takes 8.76 ms to complete the flows, compared with 2.17 ms for the reference. It also causes 1030 retransmissions. The 64-bit Q32.32 and Q42.22 variants complete all flows within 0.3% of the reference’s maximum FCT. They also achieve mean CWND fairness within 0.001 of the reference. 

Step 2: Performance tuning. Our initial reference PCM-Swift computation follows the built-in htsim implementation. The naive Swift computation uses a floating-point square-root (sqrt) calculation to estimate the target delay. 

Shell optimization. The fixedptc library’s baseline New-ton approximation, which implements sqrt in the ConnectX DPA shell, sustains only 0.105 million calls/s (Mcalls/s) per hardware thread (Figure 6b). An optimized digit-by-digit sqrt algorithm yields 0.532 Mcalls/s. 

Handler optimization. We further improve performance through algebraic transformations of Swift arithmetic. We replace divisions and the square root in Swift’s target-delay computation with multiply-only reciprocal and inverse-square-root operations. The transformed handler exceeds 0.9 Mcalls/s per DPA thread, with a mean processing time of approximately 1 .1 μs per input event. Cost of alternative designs. An alternative to PCM’s asyn-chronous control plane is to integrate UCCL with CCP [33], whose datapath DSL accumulates measurements and triggers reports to host-side policies through IPC. Our separate NewReno profile on the same Xeon measures 364 ns for DSL evaluation. In comparison, with operands in registers, PCM-Swift’s ACK-count accumulation (SUM) and RTT-sample update (LAST) each compile to one instruction, while its ACK trig-ger ( DELTA >= 1 ) reduces to a comparison and conditional branch. On the Xeon, signal and control exchange uses single-instruction atomic loads, stores, and additions. Swift shell invocations, including policy execution, take 66–192 ns (Fig-ure 8d). Moving CCP’s host-side policy execution onto Con-nectX would also require replacing Portus’s Rust runtime its Rust policies for the DPA’s C11 environment [35].

## 7.5 Performance Across Handlers 

We evaluate PCM handlers across the supported shells in Fig-ure 10. This experiment tests shell reuse across policies, pol-icy portability across shells, and overall handler-performance trends across platforms and algorithms. For the asynchronous CPU shell, the trace microbenchmark saturates each worker, as does the DPA benchmark. One Xeon core sustains 11.8–37.3 million asynchronous controller calls/s, and eight Microsoft 1P threads provide 12.2– 46.3 million calls/s. Falcon reports 20 million FAE events/s on one Neoverse-N1 core, sustained across connection counts through state prefetching [39, Fig. 22a]. PCM-Swift in Fig-ure 10 takes on average 77.1 ns/ACK on Xeon, comparable to the 66 ns RUE service interval modeled by Falcon’s simulator, which presumably models the performance of Neoverse-N1 cores. This result provides architectural context rather than a matched performance baseline. ConnectX’s 48 DPA threads sustain 9.5–15.1 million CC calls/s. For the simpler, less compute-intensive LB shell, the same 48 DPA threads sustain 18.6–48.8 million LB calls/s. For a lightweight scheme such as MP-RDMA, discussed in Section 5.4, these capacities approach per-packet policy demand on an 800 Gbit/s link. For Swift, the most compute-intensive algorithm, the capacity corresponds to one input event per two to three ACKs. 

## 7.6 Lessons Learned 

Optimize policies and backends independently. PCM demonstrates two levels of reuse. Vendors optimize back-end arithmetic to accelerate native execution across policies, while developers carry algebraic improvements in portable handlers across supported platforms. 

Validate numerical behavior and reaction timing. Swift’s fixed-point failure and scheduling sensitivity show why source compatibility needs behavioral validation. Accumu-lation preserves feedback counts, but delayed reactions can still reduce fairness and increase flow completion times. Use simulation to validate numerical representations and establish a workload-specific reaction budget. 

Provision NIC compute for the required reaction rate. 

Thread placement and flow-state footprint shape processing capacity: hardware threads share execution resources, and growing state increases cache pressure. Provision workers to meet the required reaction rate within these constraints. 

## 8 Conclusion 

PCM makes portable congestion management practical for high-performance RDMA. Our programming model spans eleven policies and four datapaths, from simulation and soft-ware transports to NIC offload. PCM policies sustain per-chunk control at 1.56 Tbit/s goodput in UCCL and achieve near-per-ACK processing capacity on vendor 400G and 800G NICs. In Proceedings of the 2015 ACM Conference on Special Interest Group on Data Communication (New York, NY, USA, 2015), SIGCOMM ’15, Association for Computing Machinery, p. 523–536. 15 A Behavioral Validation of PCM-Swift in UCCL 

We compare the CWND behavior of PCM-Swift, deployed through the reference CPU shell, with that of native UCCL Swift. We evaluate both synchronous and asynchronous PCM integrations with UCCL. The asynchronous CPU shell sup-ports relaxed and locked snapshot modes (Section 5.3). In locked snapshot mode, the datapath brackets atomic signal updates with sequence numbers. The control plane worker re-tries its sequential signal reads until the same even sequence number precedes and follows the copy. Relaxed snapshot mode accepts the first copy. We model transient network congestion by injecting a syn-thetic 500 μs RTT every 25th CC update. Figure 11 com-pares nonzero window adjustments under RTT injection for native UCCL Swift, the synchronous CPU shell, and both asynchronous snapshot modes. In the asynchronous runs, the control plane worker runs on a separate core. Across all modes, the range of PCM-Swift’s CWND adjustments closely tracks that of native UCCL Swift. The median nonzero adjustments in relaxed and locked snapshot modes differ by 1.2%. Their 1st and 99th percentiles differ by less than 1%. The datapath observes an unchanged window in 10.9% of samples in relaxed snapshot mode and 10.7% in locked snapshot mode.
