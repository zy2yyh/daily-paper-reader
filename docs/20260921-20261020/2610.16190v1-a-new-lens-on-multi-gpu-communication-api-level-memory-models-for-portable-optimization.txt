# A New Lens on Multi-GPU Communication: 

# API-Level Memory Models for Portable Optimization 

Johnathan Alsop, Bradford Beckmann, Brandon Potter, Jiakun Yan, Aurelien Bouteiller, 

Omri Mor, Tony Tye, Sameer Sahasrabuddhe 

AMD 

Abstract — As network communication increasingly be-comes a performance bottleneck for ML and HPC workloads, it is more important than ever to optimize multi-GPU data trans-fers. Recently, low-level device APIs have emerged that allow programmers to perform fine-grain optimizations via one-sided put/get operations triggered directly from the device. However, the communication libraries providing these device APIs (e.g., rocSHMEM, MSCCL++, and NCCL/RCCL GIN) currently lack a rigorous memory model defining how their primitives in-teract with the underlying memory systems. Without this, emerging HPC and ML workloads aggressively optimizing net-work communication via device APIs can be brittle, error-prone, and face compatibility and inter-operability challenges. 

This paper proposes the use of API-level memory models for these emerging device communication APIs. An API-level memory model defines the memory semantics of communica-tion API calls in a way that abstracts lower-level details from the API user and simplifies development. This work defines one such model for device-side communication (implemented in 

AMD’s recently open sourced rocSHMEM library) and demon-strates how formal relaxations to such a model can enable low-level LLM performance optimizations while retaining a well-defined standardized interface. Specifically, we describe how updating the SHMEM API implemented by rocSHMEM can properly support cache bypassing for network data, improving performance of a collective communication workload by up to 2.48x, a fused compute+communication workload by up to 1.77x, and a state-of-the-art expert-parallel communication workload by up to 1.18x. 

I. INTRODUCTION 

The rise of deep learning and large language models (LLMs) has led to powerful AI models with billions to trillions of pa-rameters. The recent growth of these models and the associated explosion of memory and compute demands motivate the use of large networks of compute devices for performing training and inference. Scaling across vast numbers of devices requires utilizing many forms of ML parallelism and frequent commu-nication and synchronization between devices. Furthermore, as HPC and ML applications scale to an ever increasing number of compute devices, communication is becoming an even greater performance bottleneck. 

Distributed applications commonly leverage communica-tion libraries with standardized APIs to simplify programming and hide the low-level details of inter-device data transfer. These APIs generally offer an easily addressable partitioned global address space and one-sided asynchronous communica-tion primitives like put and get that avoid the performance overheads of blocking for long-latency network operations. Fi-nally, specialized ordering operations enable flexible and tar-geted synchronization of these asynchronous primitives. Stand-ardized APIs like OpenSHMEM  [9]  (abbreviated here as SHMEM) and MPI  [10]  have supported these properties for decades in the CPU domain, and they are increasingly used (or will soon be adopted) in industry leading GPU ML libraries 

[1] [11]  [12] [28][29][30] [31] .

Standardized APIs support cross-company innovation. They enable inter-operability of applications with a multiplicity of vendor implementations, and they limit complexity through a separation of concerns. This allows both implementers and us-ers of an API to safely and independently introduce optimiza-tions into their code, as long as they respect the API guarantees. However, the way current communication APIs define these guarantees has been imprecise, particularly for non-CPU sys-tems. Communication operations can require complex network-dependent interactions between software threads and/or dedi-cated hardware units. In addition, GPU threads communicating through memory often require different and more complex co-herency characteristics than CPU-only systems. With both GPU hardware and software evolving rapidly, imprecise specifica-tion complicates the creation of performant and portable code. We therefore need formal specifications of memory ordering to enable aggressive optimization on both sides of the API while ensuring correctness.

To this end, we propose the use of an API-level memory model for communication, and we define one such model spe-cifically for SHMEM. An API-level model is a contract be-tween an application developer and an API implementer that specifies how the API interacts with the underlying memory system.  Figure 1  reflects the API-level memory model’s posi-

tion in the software stack. In contrast with existing memory models that describe interactions at the level of the Instruction Set Architecture (ISA) or Programming Language (PL), an API-level model operates on higher-level API operations (put, get, barrier, etc.). In GPU device-side communication libraries, these operations can be coarse-grain, paired with other opera-tions, and/or asynchronous. We formally integrate these prop-erties into an underlying PL-level memory model by 1) defining the observable accesses of each API operation, 2) fusing paired operations into a single event, and 3) breaking program order for these observable accesses and defining new relations to en-force API-specific ordering constraints. 

In addition to improving programmability, a formal API-level memory model provides a basis for optimized variants of the API. We describe one such variant and we detail the seman-tic extensions needed for GPU device-side communication APIs to enable this optimization. Once again, formal specifica-tion is necessary here so that API users and developers know and agree upon which ordering constraints will be preserved, weakened, or strengthened. 

This work makes the following contributions: 

1.  We identify limitations in existing network communi-cation API specifications and introduce the notion of a formal API-level memory model to address them. 

2.  We define and validate an axiomatic API-level memory model specifically for the SHMEM API that leverages and extends familiar consistency relations and semantics to specify memory ordering for API operations and their accesses. 

3.  We describe how the existing SHMEM and RCCL/NCCL GIN APIs and our newly defined API-level mod-els can be extended to enable a communication optimization: targeted ordering for network data. We then demonstrate the performance benefits of this optimization for some important communication patterns, showing speedups of up to 2.48x. 

II. BACKGROUND 

A. Memory Consistency Models 

A Memory Consistency Model (MCM) defines what values loads are allowed to return in a multi-threaded program. To-

day’s MCMs are frequently defined at the ISA-level (e.g., TSO 

[2]  and PTX  [3] ), or the PL-level (e.g., C++  [14] , Java  [15] , or HSA  [16] ). These represent a contract between layers of the compute stack; they define allowable behavior for developers above the MCM layer, and theyrestrict legal reorderings by software and hardware below the MCM layers. 

One common way to formally specify a MCM is via axioms over relations. Axiomatic formalization begins by enumerating 

all possible “candidate” executions of a parallel program. In de-

fining these executions, loads may return the value of aconflicting store anywhere else in the execution, or the initial memory value at that address (i.e., allowing all possible reor-derings). We then define relations between accesses in candi-date executions, and based on properties over these relations, we define which executions are legal (restricting the reorderings that are permitted). The following sections rely on language and terminology used in past works to describe this formalism  [13] .

a) Sequential Consistency for Data Race Free (SC for DRF): Modern systems use relaxed memory models that permit important reorderings at the microarchitecture and compiler levels. Although these are more complex than sequential consistency (i.e., consistent with an in-order interleaving of all thread accesses), or SC, this complexity is frequently mitigated by the use of the SC for DRF paradigm. As defined by Adve et al.  [4] , an SC for DRF model defines explicit synchronization semantics (e.g., acquire and release atomics) that must be used when communicating between threads to protect non-

synchronizing “data” accesses. If proper synchronization is used, then a program is guaranteed to be SC. 

Formalizing SC for DRF begins with defining SC axiomat-ically (as shown in Figure 2) based on a set of baseline relations: 

program order ( po ) relates all accesses within a single pro-gram thread based on the order they are evaluated; reads-from (rf ) relates loads to the store that produced the returned value; 

coherence order ( co ) relates stores to the same address based on the order they arrive in memory; and from-reads ( fr ) re-lates reads with subsequent writes to the same address in co 

(defined as rf -1 ;co ). synchronization order ( so ) relates ac-cesses that establish a rf relationship across threads and legally synchronize by using acquire and release atomic semantics. 

happens-before ( hb ) leverages so and po to relate events that are guaranteed to happen in a specified order according to the memory model. data race ( data_race ) is defined as two conflicting data accesses where at least one access is a store, and they are not related by hb in a candidate execution. If all SC executions are free of data races, then the program will be SC. If data races exist, then behavior is undefined. Given the advantages of SC for DRF and its ubiquity in modern CPU and GPU systems, we assume the use of SC for DRF (or DRF for short) PL-level memory models going forward.

C. The SHMEM API 

While the ideas in this work can apply to most GPU device-side communication APIs, we focus on SHMEM  [6] [7]  because of its widespread use in HPC and increasingly in ML frame-works. In this section we provide background on the SHMEM API with a focus on aspects relevant to memory consistency. 

1) SHMEM Overview 

SHMEM defines a set of functions, or operations, that can set up the SHMEM environment, access memory, transfer data between processing elements (PEs) in a network, and/or order other operations. SHMEM relies on a symmetric heap for sim-plified addressing in a partitioned global address space (PGAS). Accesses only conflict if they target the same address and the same PE. Operations can additionally specify a context (order-ing domain) and a team (a subset of PEs that can communicate). 

2) SHMEM Operations 

A representative subset of MCM-relevant SHMEM opera-tions are listed in  Table 1  (see the OpenSHMEM specification 

[9]  for the full set of operations and their variants). They are classified into four broad types : remote memory access rou-tines (RMA) perform bulk data transfers between PEs; syn-chronizing operations (SO) can be used to access synchroni-zation variables; collective routines (Col) are operations that span multiple PEs in a team, and ordering operations (Ord) 

order the visibility of SHMEM operations (discussed next). Many of these operations have blocking and non-blocking var-iants. 

3) SHMEM Ordering Constraints 

Here we summarize and categorize existing SHMEM order-ing semantics. Section  IV  identifies ambiguities in this specifi-cation, then formalizes the concepts, resolving the ambiguities. 

Implicit local visibility: Although not explicitly specified by the API, local memory accesses from a PE prior to a SHMEM operation on the same PE should be visible to that op-eration. That means if a thread stores to a buffer, then issues a SHMEM put operation targeting that buffer, the prior buffer stores will be visible to the put operation. 

Local completion ordering: For blocking remote memory access operations, the local accesses associated with the transfer 

(e.g., local reads for a put, local writes for a get) must “com-plete” before the API call “returns .”

Remote delivery ordering : SHMEM specifies that a

fence orders the “delivery” of SHMEM operations from the same context at a remote PE, if those operations are separated by fence and target the same PE. fence also orders prior memory accesses with subsequent remote SHMEM operations. However, it does not order prior operations with subsequent memory accesses and it does not order operations to different PEs. 

Remote completion ordering : barrier and quiet op-erations go further than fence in that they do not “return” until 

all prior SHMEM operations in the same context and their as-

sociated (local and remote) accesses have “completed .”

Synchronization requirements : Only the synchronizing and collective operations defined above can be used to synchro-nize between PEs (not RMAs). In addition, synchronizing op-erations must use a compatible context and team, and every dy-namic collective operation must be matched with a correspond-ing call issued in the same order in each member of the associ-ated team. If these rules are violated, behavior is undefined.

III. RELATED WORK 

API memory models build upon a large body of past memory consistency formalization research 

[2] [3] [4] [5] [13] [14] [15] [16] [19] [20] [22] [23] [24] . These past efforts formalize the semantics of existing weak memory mod-els, and, in some cases, they prove the correctness of compila-tion strategies or verify the legal behavior for relevant code pat-terns (litmus tests). However, their focus on PL-level and ISA-level semantics (semantics of loads, stores, and low-level syn-chronization actions) sets them apart from this work, which fo-cuses on the semantics of higher level SHMEM operations (e.g., put, get, reduction, etc.) This difference presents new formali-zation challenges when integrating API semantics with a PL-level model, and it complicates similar validation efforts for compilation (there are many correct ways to “lower” an API 

operation to PL-level) and litmus tests (correct behavior for such tests has not previously been formally defined). 

Batty et al. define a methodology for abstracting library se-mantics for C programs into high-level guarantee and deny re-lations over a history of call and return events  [21] . This pro-vides behavioral guarantees for library users without requiring them to understand library internals, similar to an API-level model. However, this methodology is designed to be general enough for any potential library. As such, it places limits on li-brary usage (a non-interference requirement restricts user and library code to communication solely through call and return semantics) and it prevents the simpler and more targeted defi-nitions of ordering semantics and optimizations that are possi-ble when considering a specific library (e.g., SHMEM). 

Recent work by Ambal et al.  [25]  and Dan et al.  [26]  for-malizes the behavior of remote direct memory access (RDMA) put and get operations on CPU devices. Similar to SHMEM put and get operations, these require integrating a notion of asyn-chrony into the memory model. However, the semantics are tied to stronger (SC and TSO) CPU memory models and low-level RDMA implementation details (queue pairs, request and re-sponse buffers, poll operations, etc.), limiting their portability to more relaxed systems (e.g., GPUs) and different networking technologies. In contrast, the API-level model described here integrates with a relaxed SC for DRF model and presents a higher level SHMEM interface that offers more flexibility to both users and implementers. 

Recently, NVIDIA introduced the notion of memory syn-chronization domains to reduce the cost of synchronization ac-tions  [17] . A synchronization domain is an ID associated with each GPU kernel launch. When enabled, only cached data that was accessed from the matching synchronization domain needs to be flushed/invalidated on a synchronization event. This can limit the impact of synchronization when there are multiple con-current kernels running on a GPU, and it has a minimal impact on the SC for HRF memory model. However, synchronization domains do not reduce the overheads when only a single kernel is active, and they require the use of system-scope for any inter-kernel synchronization. 

Finally Hamidouche et al.  [31]  introduced GPU Initiated Networking (GIN) APIs into NCCL that were quickly adopted 

by AMD’s RCCL  [35] . The current synchronization rules de-fined in GIN exhibit ambiguity similar to that of SHMEM, and they disallow the targeting ordering optimizations described in this paper. 

IV. THE API-L EVEL MEMORY MODEL 

An API-level memory model represents a contract between the implementer of an API and an application programmer us-ing the interface. We first describe how the existing SHMEM specification leaves certain ordering questions ambiguous. We then provide these missing details by defining an axiomatic API-level SHMEM memory model. Finally, we describe some intuitive rules for enforcing the constraints of the formal model. 

A. Limits of the SHMEM Specification 

The SHMEM specification summarized above uses CPU-centric language to define the ordering constraints of SHMEM programs. It describes when an API call may “return” relative 

to the “delivery” or “completion” of various memory accesses 

and transfers, but these terms are not precisely defined. This ambiguity can lead to performance and correctness challenges on emerging systems. To illustrate these challenges, consider the program depicted in  Figure 3 . PE0 performs multiple ac-cesses to local memory, then issues a put_signal operation that transfers some of the accessed data to PE1. PE1 synchro-nizes with the signal using a paired wait_until operation, then accesses the transferred data and issues a get targeting the remaining data previously stored on PE0. 

When implementing this code on a GPU or other accelerator with software-managed coherence, data visibility between ap-plication code, API code, and communicating PEs must be ex-plicitly managed. PL-level acquire and release semantics (trig-gering cache flush and invalidate operations) may be needed to make the store of A visible to the load in put_signal (i.e., if the put_signal is implemented in a separate thread), to avoid reading stale cached data after the wait_until opera-tion, and to ensure the store of B is visible to the agent imple-menting the get operation from PE1. Language in the current SHMEM specification does not clarify who is responsible for these actions, or even whether the store of B must be visible to the get ; should the application developer insert a release fence before the put_signal to ensure prior stores are visible? Do they need to insert an acquire fence after the wait_until if stale data may exist in the cache? Should these actions be han-dled by the API? Which data exactly will be made visible? When API users and developers answer these questions

The issues and code patterns described here may not be common in current distributed CPU SHMEM applications. In the following sections, we formalize how an API like SHMEM interacts with a PL-level memory model. In doing so, we aim to resolve this uncertainty and provide a basis for further refinements of the API memory model. 

B. Defining an API-Level Memory Model 

Here we define an API-level memory model that builds on top of an underlying PL-level memory model while formalizing the ordering constraints required by the API specification (or defining them where ambiguous). For simplicity, we focus on the basic DRF PL-level model described in Section  II.A , but the integration proceeds identically for consistency models with re-laxed atomics or scoped synchronization. 

A SHMEM program contains API operations alongside memory accesses within each thread. SHMEM operations are considered events ordered by po just like any other access. However, the semantics of these operations are more complex than the loads, stores and sync operations that PL-level models operate on. SHMEM operations have three general properties that must be handled for PL-model integration: 1) coarse gran-ularity, 2) multi-PE collective operations, and 3) explicit asyn-chrony. We address these challenges by 1) defining a minimal set of observable accesses for each operation, 2) fusing collec-tive multi-PE operations, and 3) breaking program order with the calling thread and introducing new relations into the memory model that enforce the API’s ordering semantics. These new events and relations are then used to extend the def-initions of hb , data_race , and sc in an API-level DRF memory model. 

1) Minimal Observable Memory Accesses 

We first define how operations access memory. For the pur-poses of the API-level SHMEM memory model, we only con-sider accesses that are observable to the SHMEM user. This is a minimal set that does not include accesses to intermediate buffers and synchronization structures, which are implementa-tion specific and should not be user-visible.  Table 2  provides the minimal observable memory accesses for a subset of SHMEM operations. SHMEM operations can access data in lo-cal and remote PEs, so observable accesses must also specify the PE ID. Note that some operations access multiple memory locations (coarse-grain operations), and some do not have any observable accesses (ordering-only operations) and are mainly used for synchronization and constraining asynchrony. For coarse-grain remote transfer operations where the source and destination targets are simply specified as a range of addresses (put, get), the full range of addresses are assumed to be accessed in a single event. 

2) Fusing Multi-PE Operations 

SHMEM and similar communication APIs have collective operations that synchronize across multiple PEs in a team, in some cases without any observable synchronizing accesses (e.g., barrier). We merge these operations into a single event for the purposes of the memory model. This single operation and any associated observable accesses are considered to be exe-cuted collectively by all nodes in the synchronizing set of PEs, allowing us to establish ordering relations across these PEs. 

3) Relations on SHMEM Operations and Accesses 

To support asynchronous (non-blocking) operations in SHMEM, the observable accesses associated with a SHMEM operation are NOT related by po with accesses from the calling thread . Conceptually, it is as if each operation issues its ac-cesses from a separate thread (which is consistent with how they will often be implemented). A po relationship is, however, ap-plied between observable accesses within the SHMEM opera-tion, but only if 1) they exhibit a true data or control depend-ency, or 2) the API specifically constrains reordering (this is the case for put_signal , where all put accesses are po ordered with the final signal access). Since the po relation does NOT 

exist between an operation’s observable accesses and normal memory accesses in the calling thread, these accesses can form a data race with each other.

C. Enforcing the API Memory Model 

Adhering to the above SHMEM API-level model can be achieved by implementing SHMEM such that PL-level hb or-dering is established for each added hb_api relation. This pre-vents reordering for relations that may participate in an 

hb_api chain, which includes ilv , lco , rdo , rco , and aso .Here we describe what is necessary for a generic HSA PL-level memory model where the SHMEM implementation may or may not offload SHMEM operations to a separate thread or hardware unit (referred to as the operation executor). 

ilv and lco can be preserved by using acquire/release se-mantics to synchronize between the calling thread and the op-eration executor (required only if they are not the same thread). In addition, for blocking synchronization operations that read local memory, lco requires acquire semantics to be associated with the read since this can be used (along with aso ) to estab-lish an hb_api chain between synchronizing PEs. Preserving 

rdo and rco requires tracking the status of pending remote operations via a shared memory structure and blocking subse-quent operations and/or accesses until prior operations reach a defined status (e.g., ordering on the network, or remote comple-tion). They additionally require release semantics, since they may be used to establish hb_api ordering between a prior lo-cal access and a subsequent remote operation that targets the same variable. Preserving aso ordering requires that any ob-servable accesses that may participate as a reader or writer in an 

aso relation use atomic semantics in the SHMEM implemen-tation to avoid legally synchronizing API operations from in-troducing a PL-level data race.

We validate the API-level model described above by imple-menting it in Alloy  [33]  and verifying expected behavior for a range of litmus tests. This implementation is applied on top of a formali zation of the LLVM compiler infrastructure’s memory

The minimal ordering is applied to en-sure the unsatisfiability of the non-SC behavior. In addition, we generate variants of these tests in two ways: 1) We revert some of the API calls to normal memory accesses to test interaction of SHMEM semantics with PL-level ordering constraints. 2) We relax the ordering constraints in the tests in order to induce non-SC behavior and/or data races. This is accomplished by re-moving fences or downgrading API calls (synchronizing->non-synchronizing calls, quiet->fence, or lco-carrying local access -> non-lco remote access). The message passing litmus test and its variants are provided as examples in  Figure 8 .

Across all litmus tests, we successfully used Alloy to vali-date that the expected SC, non-SC, and racy behavior is ob-served under the formalized SHMEM memory model.

As discussed in Section IV.C, a GPU-based SHMEM im-plementation requires acquire and release semantics to preserve ordering for SHMEM operations and data accesses, which trig-ger cache flush and invalidate actions in GPUs. These actions add latency and unnecessarily degrade cache reuse for unrelated accesses. We propose a more targeted ordering semantic that avoids the need for flush and invalidate actions by only estab-lishing ordering communicated data, and using cache bypassing when accessing this data. 

This relaxation can be exposed at the API-level memory model through a new property we refer to as a communication ID, or com_id. A com_id is associated with each SHMEM op-eration 3 and with each memory access. Users may dynamically associate com_id with individual accesses and operations, or they may statically assign a com_id to a memory allocation such that all accesses to that allocation use the associated com_id. If not explicitly specified, a default global com_id is used. 

Each of the API ordering relations described previously is defined per com_id. Each com_id-specific relation is relaxed to only order non-observable accesses if their com_id is <= the com_id of the inducing operation, and the com_id of the induc-ing operation is <= that of the relation (the global com_id is > all other com_ids). This is formalized in the updated ilv defi-nition shown in  Figure 7  (changes highlighted in red, similarly applied to lco , rdo , and rco ). The added requirements ensure

A. SHMEM Backend Modification: IPC and GDA 

We implement the the cache bypassing optimization in two rocSHMEM backends: inter-process communication (IPC) backend for intra-node communication over xGMI, and the GPUDirect Async (GDA) backend for inter-node communica-tion over InfiniBand. IPC is used for all workloads; GDA is only evaluated with DeepEP. 

In the baseline IPC implementation, a put operation copies data between PEs via normal load and store operations since PEs share a global address space. GDA implements put and 

signal by enqueueing a request packet on a send queue and updating a doorbell variable to signal to the NIC that the request packet and input buffer are ready for transfer, using release se-mantics on the doorbell update to establish ilv ordering. Both IPC and GDA use system scope release semantics in fence 

operations to establish rdo ordering, and acquire semantics in synchronizing read operations like wait_until to establish 

lco ordering. These acquire and release semantics are lowered to L2 cache flush and invalidate operations, as well as 

waitcnt instructions (these block further access until prior memory operations have completed), as illustrated in  Figure 9 .

When we apply targeted ordering, the acquire and release semantics of the put , fence , and wait_until operations only need to order data with the specified com_id. We define the target com_id to apply specifically to communicated net-work data buffers, and we only use cache bypassing accesses for this data. When targeted ordering is enabled, the flush and invalidate associated with acquire and release semantics are re-moved; only the waitcnt instruction remains to block until any pending thread accesses have completed. This provides both a latency and a cache efficiency benefit. 

B. Targeted Ordering Workloads 

We evaluate three workloads using the SHMEM backends described above with and without targeted ordering. xGMI con-nects GPUs within a node, and InfiniBand connects GPUs across different nodes. The workloads are reduce-scatter (RS), fused GEMM+reduce-scatter (GEMMRS), and DeepEP. All communication kernels are profiled running on a single com-pute node. DeepEP is additionally profiled running and across two compute nodes. Each compute node contains eight AMD Instinct ™ MI300X GPUs. The IPC SHMEM backend is used for communication between GPUs on the same node, which are connected via xGMI. The GDA backend is used for communi-cation between GPUs on different nodes (DeepEP only), which are connected via InfiniBand. 

a) Reduce Scatter (RS): RS is single-kernel communication collective workload. It is commonly used in the ML and HPC domains, and exhibits high regularity, low cache reuse, and network-limited performance. Each GPU launches multiple workgroups, and in each iteration a workgroup transfers a vector of data to all other PEs, waits to receive a vector from each PE, and reduces the received vectors. We evaluate RS for a range of vector sizes with the IPC backend only, with each GPU transferring between 128KB and 256MB of data to remote PEs using a constant number of workgroups (128 workgroups, each composed of 512 threads). 

b) Fused GEMM+Reduce-Scatter (GEMMRS): 

GEMMRS represents an additional level of workload complexity, fusing a GEMM compute kernel with a dependent reduce-scatter to achieve compute-communication overlap. GEMMRS exhibits high regularity, while cache reuse and the performance-limiting resource depend on the GEMM dimension. In GEMMRS, each GEMM output tile is transferred to a remote PE as soon as it is computed. As with RS, after transferring the chunks to the appropriate PEs, a workgroup waits until incoming transfers complete and reduces them with the local data for that PE’s partition . Unlike RS, each workgroup operates on a fixed size output tile (128 elements), with the number of workgroups growing with the size of the output matrix. This avoids coarse-grain dependencies and allows network transfers from earlier workgroups to proceed concurrently with compute from later workgroups. The GEMM sizes are chosen to resemble common LLM decode workloads, with N and K dimensions (a proxy for LLM hidden dimensions) ranging from 4K-16K, and M dimension (a proxy for batch size) ranging from 1-256. While more complex than RS, GEMMRS is still a single kernel with a regular access and communication pattern. 

c) DeepEP: DeepEP is a state-of-the-art communication library for expert parallelism, originally introduced in DeepSeek [1]. This workload exhibits irregularity (input-dependent token to expert routing), low cache reuse, and network-limited performance. It implements GPU kernels for the dispatch and combine stages surrounding the MoE feed-forward layer. DeepEP provides two kernel variants, optimized

VIII. TARGETED ORDERING PERFORMANCE EVALUATION 

Figure 10  plots the per-GPU network bandwidth achieved by RS with and without targeted ordering for the IPC backend. Targeted ordering improves performance by up to 2.48x for the IPC backend by avoiding the latency cost of cache flush opera-tions. The greatest performance gains are at smaller transfer sizes where the relative impact of the flush latency is greater. At larger transfer sizes, performance is increasingly limited by network bandwidth rather than latency (both configurations sat-urate at around 220GB/s per GPU, which is roughly 50% of the theoretical peak), and the optimization benefit diminishes. 

Figure 11  plots the relative speedup of targeted ordering for GEMMRS across a range of GEMM sizes with the IPC backend. At these sizes, GEMMRS performance is primarily limited by communication latency and/or memory bandwidth. The benefit of targeted ordering comes from avoiding flush la-tency AND avoiding the impact of flush and invalidate opera-tions on cache reuse, since the SHMEM operations are executed concurrently with GEMM compute. As the M dimension grows, cache reuse potential for the GEMM operation increases (the KxN weight matrix is accessed M times), and more SHMEM transfers are necessary (the MxN output matrix is transferred in fixed tile sizes), so targeted ordering benefit increases. As N and K dimensions grow, the GEMM operation increasingly forms a performance bottleneck, so targeted ordering benefits are re-duced. Overall, targeted ordering offers up to 1.77x speedup for GEMMRS on IPC. 

Figure 12  plots the relative speedup of targeted ordering for DeepEP across a range of token counts with both IPC and GDA backends. Similar to RS, DeepEP is purely a communication workload, and the primary benefit of targeted ordering comes from avoiding flush latency rather than cache effects. Although the irregularity of DeepEP leads to some fluctuation in perfor-mance across token counts, targeted ordering consistently pro-vides between 10-20% speedup relative an unoptimized base-line for most token counts. The largest gains (1.18x for both IPC and GDA) are seen at lower token counts; this is consistent with the bandwidth benefits seen for the simpler RS workload, and is explained by the diminishing benefits of latency saving as performance becomes more throughput limited. Note also that speedups drop off earlier for the GDA backend, which has a lower peak bandwidth that can be saturated earlier. 

IX. CONCLUSION 

Communication APIs can simplify distributed program-ming for emerging ML workloads, but ambiguity in their spec-ification leads to uncertainty for users and implementers. By formalizing an API-level SHMEM memory model, we provide a precise specification that enables safe optimization on either side of the API. We highlight this flexibility by formalizing the targeted ordering optimization for network data. Targeted or-dering avoids costly flush and invalidate operations in SHMEM calls, leading to multiple sources of performance improvements (up to 2.48x) across multiple communication patterns and backends. By formalizing this optimization as an extension to the memory model, we make the optimization and associated ordering implications opt-in, and we ensure that users and im-plementers of the API agree on guaranteed behavior.
