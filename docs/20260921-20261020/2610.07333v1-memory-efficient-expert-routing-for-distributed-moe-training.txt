## Abstract 

As Mixture-of-Experts (MoE) models scale toward hundreds of experts and higher top-k routing, memory efficiency in dis-tributed training becomes a critical bottleneck. Peak memory is dominated by the MoE block, not attention: every inter-mediate buffer in the MoE dispatch pipeline is individually scaled by top-k routing. The standard all-to-all dispatcher sends all routed tokens in a single collective step, requiring the full top-k-expanded buffer to be constructed at once. In this work, we propose RelayMoE , a ring-based MoE ex-ecution model that computes locally as expert weights or to-kens circulate, avoiding full top-𝑘 -expanded dispatch buffers. 

RelayMoE selects between expert and token routing accord-ing to communication volume and overlaps transfers with computation. The ring structure naturally supports memory-efficient MoE recomputation during backward: each hop reconstructs expert intermediates, uses them to compute gradients, and releases them before the next hop. The saved memory supports longer sequences and larger batches, or retains more attention activations to reduce attention re-computation and improve training throughput. We evaluate 

RelayMoE on 30B–57B production MoE models and varied expert configurations. In single-layer MoE experiments, Re-layMoE achieves a 2 × average speedup over Megatron-LM. In full-model training under the same GPU memory bud-get, it improves throughput by up to 2.02 × and extends the largest tested trainable sequence length by up to 2.85 ×.

## 1 Introduction 

The rapid scaling of large language models (LLMs) has in-creasingly relied on Mixture-of-Experts (MoE) architectures. By activating only a subset of experts per token, MoE models achieve stronger quality at a fraction of the compute cost of dense models [6, 8, 30], making them a common architec-ture for frontier systems. This advantage has led to larger and sparser MoE configurations along multiple dimensions simultaneously: more experts, higher top-k routing, longer training sequences, and wider expert Feedforward Network (FFN) layers, as shown in Table 1. To train these increasingly large MoE models, expert par-allelism (EP) [30, 35] distributes experts across GPUs and dispatches tokens to their assigned experts via all-to-all col-lective communication. Because each token is replicated to its top-k selected experts, every intermediate buffer in the dispatch pipeline is 𝑘 × larger than the base activation tensor. This compounds further with increasing sequence lengths and batch sizes. As a result, peak memory from MoE dispatch has grown by an order of magnitude in recent architectures (Table 1). Meanwhile, attention memory has been effectively reduced through memory-efficient algo-rithms [3, 4, 15, 19, 24] and hybrid linear-attention designs in recent architectures [29], leaving MoE dispatch as the domi-nant contributor to peak memory. As Figure 3 shows, MoE blocks create transient memory spikes that determine the OOM boundary and limit the maximum trainable sequence length and batch size. Prior work has extensively optimized EP communica-tion. Libraries such as DeepEP [45], HybridEP [46], and NCCL-EP [10] have improved dispatch throughput and la-tency through fusing permutation with communication, and communication–computation overlap. While these techniques can reduce the number of coexisting intermediate buffers, token dispatch and expert computation still create memory

peaks that limit training (§ 2). Multiple expanded activations can coexist as dispatch and compute stages allocate new outputs while retaining their inputs. Reducing this mem-ory footprint requires rethinking how communication and computation are organized in the MoE block. Tutel [14] pipelines token dispatch and expert compu-tation using multiple streams, while FasterMoE [13] uses fine-grained scheduling to overlap communication with com-putation. Janus [25] instead fetches expert weights to process local tokens. These works primarily target communication efficiency, while peak GPU memory during MoE execution remains a limiting factor, especially during backward. In this paper, we present RelayMoE , a ring-based MoE execution model that reduces peak GPU memory by com-puting locally as data circulates through the ring. RelayMoE 

circulates expert weights or token activations through a ring of GPUs. At each hop, a GPU computes partial results using the data present on that device and forwards the visiting data to the next GPU; the partial results accumulate into the final output as the data completes the ring. Because no GPU ever needs to receive and hold data from all other GPUs, the memory footprint of the MoE block is capped by the local data plus a fixed number of in-flight partitions, independent of the top-𝑘 factor and the EP degree. Rather than reserving a fixed token capacity for each expert, RelayMoE processes the routed token–expert pairs partition by partition. This enables dropless, padding-free expert computation and sup-ports longer sequences and larger batch sizes on the same hardware. To turn these memory savings into higher training through-put, RelayMoE selects between expert and token routing ac-cording to communication volume and overlaps transfers with local computation. Memory efficiency must also extend to backward: activation checkpointing discards forward in-termediates, but reconstructing them together can recreate a large memory peak. Reconstructed activations remain in memory while gradient computation produces additional intermediate tensors. The ring structure naturally supports memory-efficient MoE recomputation during backward: at each hop, RelayMoE reconstructs the intermediates needed for local gradient computation and releases them immedi-ately afterward. This prevents expert intermediates from accumulating across hops and leaves more memory for re-taining attention activations, reducing attention recomputa-tion. We make the following contributions: 

• We identify the memory overhead of full top-𝑘 -expanded dispatch buffers and propose a ring-based MoE ex-ecution model that avoids materializing them, with adaptive routing between experts and tokens. 

• We design memory-efficient MoE recomputation that reduces the backward memory peak without an addi-tional ring traversal, and selective attention recompu-tation that converts these memory savings into higher training throughput. 

• We evaluate RelayMoE on production MoE models and across varied expert configurations. Compared with all-to-all, RelayMoE achieves a 2 × average speedup in MoE layer execution at EP=8, reduces peak GPU memory during MoE execution by 7.6 × on average at EP=64, and extends the largest tested trainable se-quence length by up to 2.85 × in full-model training.

2.2 Peak Memory Consumption in MoE Training 

To understand where peak memory arises in distributed MoE training, we profile a Qwen3-style MoE model (Ta-ble 3) with results shown in Figure 3 and 4. Each of the 4 transformer layers consists of a multi-head attention block followed by a MoE block with top-8 routing. We train with a micro-batch size of 24 and sequence length of 16384 on 8 H100 GPUs. For the attention portion of each layer, we ap-ply tensor parallelism with sequence parallelism (TP=SP=2) and context parallelism (CP=4), which together reduce the local sequence length to 2048. For the MoE portion, we use expert parallelism (EP=8) with expert tensor parallelism dis-abled (ETP=1), following MoE Parallel Folding [23] where attention and MoE adopt independent parallelism mappings. Activation recomputation is enabled throughout. ## 3 Design 

RelayMoE reduces peak GPU memory by computing locally as data circulates through a ring. We describe ring-based dispatch and its communication–computation overlap in Section 3.1, adaptive routing in Section 3.2, memory-efficient MoE recomputation in Section 3.3, and selective attention recomputation in Section 3.4. 

3.1 Ring-Based MoE Dispatch 

RelayMoE circulates data through the expert-parallel group in a ring instead of gathering all routed tokens in a single step (Figure 5). Both the experts and the tokens are partitioned across the EP group: each rank hosts a subset of the experts, as in standard expert parallelism, and holds the tokens of its local batch. We illustrate ring execution using expert routing; Section 3.2 discusses token routing and the choice between the two modes. At each hop, a GPU computes partial results using its local tokens and the visiting expert partition ,accumulates them into the output, and forwards the expert weights to its ring neighbor via peer-to-peer communication. After 𝑁 computation hops across the 𝑁 GPUs in the EP group, every partition has visited every GPU, so each token has been processed by all of its assigned experts and the output activation is complete. 

Forward execution. To illustrate, consider a forward hop using expert routing. The GPU uses the routing map to find which local tokens selected any of the visiting experts. For matching pairs, it locally permutes the relevant tokens, exe-cutes the expert GEMM, weights the outputs by the router probabilities, and adds the results to the running output ac-tivation. Tokens that did not select any visiting expert are skipped. Thus, each hop computes only the token–expert pairs selected by the router, while the expert partition follows the fixed ring schedule.

RelayMoE is mathematically equivalent to all-to-all dis-patch. Each token–expert pair computes the same GEMM with the same weights and the same router probabilities. The difference is the execution order: all-to-all gathers the pairs at the destination GPU before computing, while RelayMoE 

accumulates partial outputs incrementally across hops. 

Communication–computation overlap. Ring-based dis-patch replaces the all-to-all dispatch pipeline with a sequence of peer-to-peer hops. Although this avoids the full expanded dispatch buffers, performing computation and communica-tion sequentially at every hop would add substantial latency. Overlapping them is therefore critical to making ring-based dispatch practical. Forward requires overlap between local computation and weight transfer; backward additionally re-quires weight gradient transfer. We describe the schedule with expert routing below. Token routing follows the same principle, overlapping transfer of the next token partition with computation on the current partition. In the forward pass, while a GPU computes using the currently visiting expert partition and its local tokens, it prefetches the next partition’s weights from its neighbor via asynchronous P2P communication. If this transfer completes before the current computation finishes, the next partition is available without a communication stall. With effective over-lap, the per-hop time approaches the larger of computation and transfer time, rather than their sum. During backward, RelayMoE overlaps local recomputation and gradient computation with merged transfers of expert weights and accumulated weight gradients. Gradients follow their corresponding weights one hop later, so each trans-fer combines weights and gradients from different expert partitions. The key observation enabling this overlap is that local partial weight gradients can be computed without wait-ing for the incoming accumulated gradient buffer. After lo-cal gradient computation completes, the GPU synchronizes with the incoming buffer, adds its local partial gradient in-place, and asynchronously forwards the updated buffer to the next GPU. In distributed MoE training, EP typically works along-side other parallelism dimensions that further adjust both resident memory and communication volume. Sequence par-allelism (SP) and context parallelism (CP) partition the se-quence dimension, reducing tokens per GPU to 𝐵 × 𝑆 /( SP ×

CP ). Expert tensor parallelism (ETP) splits each expert’s weight matrices across GPUs, reducing per-expert weight size to 𝑊 /ETP. MoE Parallel Folding [23] allows ETP to be configured independently of attention-layer TP. Both adjust-ments apply to both modes, as shown in the second section of Table 2. Because these adjustments can shift the balance in either direction, the preferred routing mode depends on the full training configuration rather than the model architecture alone. For example, a model with many experts may favor expert routing under high ETP (which shrinks expert vol-ume) but token routing under low ETP. RelayMoE evaluates both volumes at training start using the full configuration and selects the mode with lower per-hop communication. As shown in Table 1, frontier MoE models have grown from 8 experts (Mixtral) to several hundred (Qwen3.5, Kimi K2). At a fixed EP degree, this increases the number of ex-perts per GPU 𝐸 /𝐸𝑃 . For a fixed expert size, more experts increase the weight volume transferred at each hop under expert routing. Token routing avoids transferring these ex-pert weights, making it an attractive option when expert partitions are large relative to token activations. The choice still depends on expert width and token count. The physical topology of the ring also matters. When EP spans multiple nodes, cross-node hops use inter-node links (e.g., RDMA) with substantially lower bandwidth than intra-node NVLink. All-to-all dispatchers address this through hierarchical algorithms and optimized kernels such as Tutel and DeepEP that pipeline cross-node transfers. RelayMoE ’s ring structure instead serializes communication into P2P hops, which creates opportunities to overlap each hop’s trans-fer with local computation (Section 3.1), but requires careful scheduling to avoid underutilizing bandwidth on the fast intra-node hops. Its memory benefit comes from avoiding the full expanded dispatch buffers, while its latency depends on the balance between local computation and transfers over the available links.

3.4 Selective Attention Recomputation 

The memory saved by RelayMoE can also reduce recomputa-tion outside the MoE layer. We retain the MoE recomputation schedule above and use the available memory to selectively retain attention activations. These activations can then be reused during backward, reducing attention recomputation and improving training throughput. For each attention layer 𝑖 , recomputation option 𝑗 has a memory cost 𝑚 𝑖,𝑗 for retained activations and a compute saving 𝑐 𝑖,𝑗 from avoiding the corresponding backward recom-putation. Both are estimated from the model configuration and parallelism settings. For grouped-query attention with FlashAttention, the activation sizes depend on the micro-batch size, local sequence length, number of attention heads, and head dimension. The compute saving also depends on sequence length and the attention mechanism used by each block. 

RelayMoE uses the difference between GPU capacity and peak memory under full recomputation as its memory bud-get. It ranks the available options by their compute saving per unit of memory 𝑐 𝑖,𝑗 /𝑚 𝑖,𝑗 and greedily selects options within this budget. The selection is computed once at the start of training and applied throughout. 

## 4 Evaluation 

4.1 Experimental Setup Platform. All experiments were run on MareNostrum 5 in the Accelerated (ACC) partition. Each node contains four NVIDIA H100 GPUs (64 GB HBM2e per GPU) and two Intel Xeon Platinum 8460Y+ CPUs (40 cores each). GPUs within a node are interconnected via NVLink 4.0, and nodes are connected through an NDR InfiniBand network with a fat-tree topology [1]. 

Software and baselines. We implement RelayMoE on top of Megatron-LM [37] in 2.3K lines of code. For the MoE layer experiments, we compare RelayMoE against FasterMoE [13], Tutel [14], and Megatron-LM’s all-to-all dispatcher, varying token counts and expert parallelism degrees. The All-to-All baseline uses the default MoE dispatcher from a recent version of Megatron-LM (May 2026). For end-to-end training, we use the same All-to-All implementation as our primary baseline. We also enable DeepEP [45] within Megatron-LM, which optimizes token dispatch and combine while retaining the same all-to-all formulation. 

Models. We evaluate RelayMoE using Qwen3-style configu-rations that vary the number of experts (64–384), the routing degree (top-4 to top-16), and the expert FFN width (512–2048). We adjust the number of layers to keep the total trainable parameter count comparable across settings, as shown in Ta-ble 3. Single-layer experiments isolate MoE execution, while full-model results also reflect the different layer counts. Un-less stated otherwise, these experiments use 2 nodes (8 GPUs) with TP=4, CP=2, PP=1, and EP=8. We also evaluate production-model training with Qwen2-57B-A14B, Qwen3-30B-A3B, and Qwen3.5-35B-A3B on 8 nodes (32 GPUs). We enable NVIDIA’s MoE Parallel Fold-ing [23], a state-of-the-art parallelization strategy that allows attention and MoE layers to use independent configurations. We use TP=2, CP=4, PP=4, and EP=8 to evaluate the benefits of RelayMoE on top of these parallelism optimizations. 

Metrics. The MoE layer experiments report forward-and-backward latency, including communication. Average speedups are arithmetic means over distinct test configurations. For full-model experiments, we report model throughput in TFLOP/s/GPU, excluding recomputation FLOPs but including recomputa-tion time. For a given model and sequence length, higher throughput means more training tokens processed per sec-ond.

4.3 Model Training Performance 

MoE-layer latency captures only part of RelayMoE ’s effect on training: lower MoE memory usage also leaves more space for attention activations and input tokens. We further quan-tify end-to-end throughput and trainable sequence lengths. 

End-to-end performance on production models. We evaluate throughput and trainable sequence length on pro-duction MoE architectures. We compare RelayMoE with all-to-all on Qwen3-30B-A3B, Qwen3.5-35B-A3B, and Qwen2-57B-A14B using 32 GPUs with TP=2, CP=4, PP=4, and EP=8. At each sequence length, we select the largest micro-batch size for each dispatcher that fits in GPU memory. Figure 11 shows that RelayMoE achieves higher throughput on both Qwen3-30B and Qwen3.5-35B at every sequence length where both dispatchers run, with the memory savings allowing larger micro-batches. The largest tested trainable sequence length increases from 393K to 786K, a 2 × improvement. These gains hold across different expert granularities: Qwen3.5-35B doubles the expert count with a narrower expert FFN. On Qwen2-57B, RelayMoE trains at 384K while all-to-all runs out of memory, demonstrating the capacity benefit on this wider-expert model. Attention and the remaining training work limit how much faster MoE execution improves end-to-end throughput; the larger feasible micro-batches and contexts provide an additional benefit from lower memory usage. 

Comparison with DeepEP. We next compare RelayMoE 

with DeepEP to evaluate training throughput and capac-ity with optimized all-to-all communication. We use the Qwen3-style full models in Table 3, including their different layer counts, and evaluate sequence lengths 40K, 65K, and 98K. Both dispatchers use EP=4 within one node; inter-node DeepEP was unavailable with the platform’s NVSHMEM and NIC configuration. Where DeepEP fits, it uses a fixed batch size and the smallest number of recomputed atten-tion blocks that fits in GPU memory. RelayMoE uses the same number of recomputed attention blocks and its largest feasible micro-batch. Figure 12 reports the results. When both dispatchers fit in memory, RelayMoE generally achieves comparable training throughput while supporting larger micro-batches. Matching the number of recomputed attention blocks excludes the reduced-recomputation benefit. The larger micro-batch does not guarantee higher through-put: H2048 remains slower for RelayMoE , although the gap narrows at longer sequences, consistent with the higher expert-transfer cost of its wide FFNs. DeepEP runs out of memory on K8 , K12 , K16 , and H512 at 98K, while RelayMoE trains these configurations. DeepEP optimizes token dispatch and combine while retaining the all-to-all formulation. Optimized dispatch kernels retain the routed-token activation buffers, so faster communication alone does not remove their memory cost [47]. Here, lower memory usage expands the trainable configurations even when throughput gains are limited. At 98K, both dispatchers still run out of memory on E64 , whose 24-layer configuration retains attention and checkpoint state across more layers; fewer experts per layer therefore do not guarantee a smaller full-model memory footprint. 

4.4 Impact of Memory Savings 

The end-to-end comparisons combine changes in MoE exe-cution with the effects of lower memory usage. We examine three uses of the saved memory: retaining attention activa-tions to reduce recomputation, increasing the micro-batch, and extending the sequence length. The sequence-length comparison holds the micro-batch and full recomputation settings fixed, showing whether the capacity benefit persists without either of the first two adjustments. 

Recompute reduction for improved throughput. 

We first evaluate whether the memory savings of Relay-MoE can be translated into higher training throughput by reducing attention activation recomputation. We use the Qwen3-style configurations from Table 3 on 8 GPUs and evaluate three long-context settings with sequence lengths 40K, 65K, and 98K. For these three sequence lengths, we use micro-batch sizes 12, 8, and 5, respectively, which keeps the number of tokens per step approximately constant. For each model configuration and each dispatcher, we calculate the number of recomputed attention blocks from the available GPU memory budget using the method in Section 3.4. Figure 13 shows higher throughput for RelayMoE in most configurations, with speedups of up to 2.02 × on K16 at 40K. The saved MoE memory allows more attention activations to be retained for backward, reducing attention recompu-tation and improving throughput. The near-parity on K4 is consistent with its lower top-𝑘 expansion, which means less memory can be saved by removing dispatch buffers. All-to-all remains faster on E384 at all three sequence lengths; H2048 is also slower at 40K and 65K, but reaches comparable throughput at 98K. For these configurations, the memory savings do not consistently offset the execution cost associated with their larger expert-weight volume. Unlike the fixed-batch latency comparison in Section 4.2, this study decreases the micro-batch as sequence length increases, keep-ing the number of tokens processed per step approximately constant. Longer sequences therefore do not provide more to-kens to amortize expert transfers. Section 4.5 examines token routing as an alternative when moving experts is costly.

## 5 Related Work 

MoE training . Existing work optimizes communication in MoE expert parallelism through dispatch libraries [10, 26, 45, 46], communication–computation overlap [5, 14, 17, 20, 27, 36, 43], and network design [22]. Other work optimizes expert computation and activation memory usage [9, 12, 42], parallelism and pipeline layouts [18, 23, 44, 48], and exe-cution on HPC platforms [41]. RelayMoE targets the top-𝑘 -expanded inter-GPU dispatch buffers. Its ring execution can incorporate optimized expert kernels and communication– computation overlap, and complements attention parallelism. To reduce communication overhead, existing work ex-plores transferring experts to GPUs that host tokens. Faster-MoE [13] replicates overloaded experts near their tokens to 

> 12

alleviate load imbalance. In its data-centric mode, Janus [25] uses credits to bound GPU expert-fetch buffers and caches fetched weights in host memory for backward. RelayMoE 

targets the peak from expert intermediates during backward, reconstructing and releasing them within each hop using the same weight transfers as gradient computation. These mem-ory savings support longer sequences, larger batches, and larger top-𝑘 values within the same GPU memory budget. MemFine [47] reduces MoE activation memory usage through token chunking and chunk-level recomputation, retaining dispatch–compute–combine for each chunk. Ring-Expert in RelayMoE likewise limits the lifetime of recon-structed intermediates, but keeps tokens local and circulates expert partitions, avoiding inter-GPU token-dispatch buffers while reusing weight transfers for recomputation and gradi-ent computation. 

Memory-efficient training . Offloading [32, 33], model-state partitioning [31], and activation checkpointing [2, 19] have been explored to reduce memory pressure in LLM train-ing. These techniques reduce GPU memory usage for model states or trade recomputation for fewer retained activations. 

RelayMoE complements them by reducing the memory re-quired during MoE execution, including the intermediates reconstructed during backward. The memory saved in MoE layers can be used to retain more attention activations, re-ducing attention recomputation and improving throughput for the same training workload. Other work reduces the memory cost of attention. FlashAt-tention [3, 4, 34] reduces attention activation memory usage, while sequence and context parallel systems distribute at-tention computation and activations across GPUs [7, 11, 15, 21, 24, 37, 40]. RingAttention also uses a ring, but circulates KV blocks for attention; RelayMoE addresses MoE dispatch buffers and expert activations. Reducing attention memory leaves these MoE costs in place, so the MoE sublayer can still limit the trainable sequence length. These attention opti-mizations and RelayMoE can be combined to reduce memory in both sublayers, supporting longer-context training under the same hardware budget. 

## 6 Conclusion 

We presented RelayMoE , a ring-based MoE execution model that avoids full top-𝑘 -expanded dispatch buffers and reduces the memory required for expert recomputation during back-ward. The saved memory supports longer sequences and larger micro-batches, and can be used to reduce attention recomputation. Our evaluation demonstrates lower peak GPU memory usage and improved training throughput over all-to-all dispatch.
