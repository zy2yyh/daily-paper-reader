## 摘要
随着工作负载需求变化，数据中心拥塞控制（CC）和负载均衡（LB）快速演进，但其部署依赖于 RDMA 硬件和传输接口。新兴的可编程 RDMA 引擎将策略代码绑定到厂商 API。因此，运维人员必须为其部署的每个平台移植每种策略。我们通过 PCM 解决这一问题，这是一种编程模型，将可移植的拥塞管理与数据中心网卡上的平台集成分离。开发者编写事件驱动处理程序，可在仿真中调试并在真实硬件上复用。PCM 将流遥测暴露为信号，并使用触发器支持逐事件反应以及对累积反馈的更粗粒度响应。厂商提供优化后端，将信号和输出控制映射到具有明确定义的反馈与控制语义的原生网卡机制。我们通过实现十一种知名的数据中心 CC 和 LB 算法来展示 PCM 的表达能力。我们在四种不同的数据路径上部署 PCM：Ultra Ethernet 模拟器、基于 CPU 的 UCCL，以及 NVIDIA ConnectX-8 和 Microsoft 1P 上的网卡内卸载。在 CX-8 上，PCM-Swift 达到的处理能力相当于在 800 Gbit/s 下每三个 4 KiB 数据包一次反应，仅使用网卡硬件线程的五分之一。在 UCCL 中，它以 64 KiB 块级控制达到与原生 Swift 的 1.56 Tbit/s 有效吞吐相当的水平。PCM 的设计为 Ultra Ethernet 正在推进的可移植拥塞管理接口工作提供了参考。

## Abstract
Datacenter congestion control (CC) and load balancing (LB) evolve rapidly as workload demands change, but deployment depends on RDMA hardware and transport interfaces. Emerging programmable RDMA engines tie policy code to vendor APIs. Operators must therefore port each policy for every platform they deploy. We address this with PCM, a programming model that separates portable congestion management from platform integration on datacenter NICs. Developers write event-driven handlers that they can debug in simulation and reuse on real hardware. PCM exposes flow telemetry as signals and uses triggers to support per-event reactions and coarser responses to accumulated feedback. Vendors provide optimized backends that map signals and output controls to native NIC mechanisms with defined feedback and control semantics. We demonstrate PCM's expressivity by implementing eleven well-known datacenter CC and LB algorithms. We deploy PCM across four distinct datapaths: an Ultra Ethernet simulator, CPU-based UCCL, and on-NIC offloads on NVIDIA ConnectX-8 and Microsoft 1P. On CX-8, PCM-Swift achieves processing capacity equivalent to one reaction per three 4 KiB packets at 800 Gbit/s, using one-fifth of the NIC's hardware threads. In UCCL, it matches native Swift's 1.56 Tbit/s goodput with 64 KiB chunk-level control. PCM's design informed ongoing Ultra Ethernet work toward a portable congestion management interface.

## 1. 核心问题与研究背景

- **背景**：数据中心拥塞控制（CC）与负载均衡（LB）随 AI 训练、集合通信、存储与分析等负载快速演进，但策略部署受限于 RDMA 硬件与传输接口。把策略硬编码进 RDMA 传输 ASIC 需要经历多年的流片、测试和部署周期，无法跟上模型、拓扑与拥塞信号的变化。
- **现有可编程方案的困境**：
  - Tonic/HotCocoa（FPGA + Verilog）：改策略需综合、时序收敛与目标相关验证。
  - AMD Pensando、Broadcom Thor Ultra：P4 类流水线与厂商编译器/阶段/元数据绑定。
  - NVIDIA DOCA PCC：C 回调绑定 ConnectX DPA 的 ABI、事件格式与流上下文布局。
  - Google Falcon：仅公开规范，异步引擎语义与事件过滤为自研。
  - Linux eBPF CC：依赖内核回调与 socket 状态，无法卸载到 RDMA 网卡。
  - Presto（Tofino 2）、UCCL（Verbs C++）：策略与 P4 数据面或特定类/路径 API 耦合。
  - CCP：用户态控制面可移植，但微秒级往返（实测 NewReno 周期 10 μs）无法满足 1.6 Tbit/s 下每 20 ns 一个 4 KiB 包的逐包决策。
- **核心问题**：缺少一种通用接口，既能让策略**源码可移植**（跨厂商、跨传输、跨仿真/硬件），又能在纳秒级数据路径上**高效执行**。
- **整体含义**：PCM 提出将“策略开发”与“平台集成”解耦——开发者写一次事件驱动 handler，厂商为每个平台实现并独立优化一次后端映射，从而把 CC/LB 创新从“每平台移植”变为“一次编写、多处生成”。

## 2. 方法论

### 2.1 核心思想：handler + specification + shell 生成

- 一个 **handler** 是有状态函数，每个 handler context 属于一条流；handler 通过统一的 `get/set` 访问器读写信号与控制、维护私有状态，不感知硬件细节。
- 开发者提供 C 源码 + **specification**（列出所用对象及属性）构成 handler package；**shell 生成器**结合平台后端 API 生成 shell，负责事件累积、触发判定、构造快照、调用 handler、提交输出。
- 成功生成 shell 即确立**源码兼容性**；部署参数（MTU、BDP）与数值精度仍按目标调整，且每个部署需做**行为验证**。后端若无法提供所需信号或执行所需控制，必须在编译期拒绝该 handler（如 ConnectX 后端因缺路径选择能力而拒绝 LB handler）。

### 2.2 五类抽象对象

- **Controls**：传输旋钮（窗口、速率、路径熵、累积信用），handler 执行后交还传输层。
- **Signals**：流遥测（ACK/NACK/RTO/ECN 计数、RTT、elapsed time、队列积压、路径 ID），每个信号指定累加器 **SUM / MIN / MAX / LAST**；累加器存储与事件数无关，多个命名信号可共享同一遥测源。
- **Triggers**：由累积事件驱动，用某信号值与静态阈值做单指令比较，后端把所有触发合并为一个 **mask** 供 handler 分支；比较模式含 **RAW**（对累积值）、**DELTA**（相对该触发器上次满足点的变化）、**MAGNITUDE**（相对同基线的绝对变化）。每个 handler 至少需一个触发信号。
- **Variables**：持久私有状态（有/无符号标量、定长数组），浮点或定点在编译期选择。
- **Constants**：流内不变状态（base RTT、MTU），编译期解析以消除冗余 load。

### 2.3 编译期优化

- 为对象建立静态内存布局，把访问器**折叠为原生 load/store**，消除运行时查表与 mask 转换。
- 把累加器更新映射到硬件原语（如 ConnectX 的事件合并、原子指令）；在 AArch64/RISC-V 上每次信号累积仅需 1 条（SUM/LAST）或 2 条（MIN/MAX）指令。
- shell 可对反馈做**单位归一化或近似**（如 10 ns 平台 tick → 100 ns PCM tick；CX-8 仅给累积 ACK 计数，用 MTU 估算确认字节数），但无法恢复平台不提供的信息。

### 2.4 执行模式与快照语义

- **同步模式**：在流事件路径上完成“累积—触发—快照—执行—提交”，信号更新与执行不重叠，可用非原子存储。
- **异步模式**：独立控制面扫描上下文并执行 handler，通过原子操作交换信号与控制（CPU 用 fetch-add/store/CAS；CX-8 由闭源 PCC runtime 在静态分配的硬件线程上完成）。
- **Snapshot**：保证 `get/set` 语义不被并发更新破坏；异步下允许 **relaxed snapshot**（每个信号保序，但 handler 可能读到不同更新 epoch 的反馈），并提供基于序列号的锁定快照与“最大偏斜”丢弃机制。

### 2.5 典型算法流程（文字描述）

- **发送端 CC（MP-RDMA 风格）**：ACKED_BYTES 用 SUM + DELTA≥1 触发；handler 用当前累积值减私有基线 `PREV_ACKED_BYTES` 得到新确认字节，推进基线，按 `cwnd += diff*MTU/cwnd` 做加性增，NACK 分支优先执行。
- **接收端 CC（EQDS）**：PULL_TARGET 用 MAX + MAGNITUDE≥1 触发，handler 将 PULL_NO 提升至不超过 target（每次最多 `CREDITS_PER_PULL`），若仍有需求则置内部 loopback 信号 NEEDS_MORE 请求再次调度。
- **LB（REPS）**：在 ACK RX 路径用私有 ECN 基线判断“本批无新 ECN 标记”，若是则把 ACK 携带的路径写入环形 EV 缓存（掩码索引、bitmap 记录有效项）；论文也指出 LAST 型路径信号无法在合并批次中保留所有 ACK-路径对应关系，精确逐包缓存更新需要相干事件投递与足够算力。
