## 摘要
分布式推理依赖于 GPU 集合通信，而集合通信必须跟得上不断演进的硬件和专用工作负载。然而，现有集合通信实现通常将语义、编排（数据在何处以及何时移动）和数据通路（数据如何移动）耦合在一起。这种耦合使得采用新的硬件机制以及为应用定制通信变得代价高昂。我们提出 Purlin，一个将这些问题分离的 scale-up 通信框架。在 Purlin 顶层，我们将集合通信指定为输入和输出布局的命名以及拷贝或归约操作。在中间层，我们引入一种共享编排协议 Stage, Notify, And Consume（SNAC），它从这些规范中推导出协调方式。SNAC 之下是称为 Atom 的硬件特定数据通路，它实现集合通信的两个关键数据移动原语：拷贝和归约。这种分离使我们能够定制集合通信并采用新的硬件机制，同时通过 SNAC 复用编排。我们在 A100、H200 和 B200 GPU 上评估 Purlin。在七种集合通信操作中，Purlin 相比基线实现最高 5.14 倍的延迟加速和最高 4.50 倍的带宽提升。集成到 SGLang 后，Purlin 将离线 LLM 服务吞吐量和交互性平均提升 1.13 倍，最高较基线提升 1.37 倍。对于在线 LLM 推理，Purlin 将交互性平均提升 1.26 倍，最高提升 2.85 倍，最大增益出现在过载情况下。对于扩散图像生成，Purlin 将端到端延迟最多降低 1.13 倍。

## Abstract
Distributed inference depends on GPU collective communication that must keep pace with evolving hardware and specialized workloads. However, existing collective implementations often couple semantics, orchestration (where and when data moves), and the datapath (how data moves). This coupling makes it costly to adopt new hardware mechanisms and customize communication for applications. We present Purlin, a scale-up communication framework that separates these concerns. At the top of Purlin, we specify collectives as a naming of an input and output layout and a copy or reduction operation. In the middle, we introduce a shared orchestration protocol, Stage, Notify, And Consume (SNAC), which derives coordination from these specifications. Below SNAC sits a hardware-specific datapath we call Atom, which implements two key data movement primitives for collectives: copy and reduce. This separation lets us customize collectives and adopt new hardware mechanisms while reusing orchestration via SNAC. We evaluate Purlin on A100, H200, and B200 GPUs. Across seven collectives, Purlin achieves latency speedups of up to 5.14x and bandwidth improvements of up to 4.50x over baselines. Integrated into SGLang, Purlin improves offline LLM serving throughput and interactivity by 1.13x on average and up to 1.37x over baselines. For online LLM inference, Purlin improves interactivity by 1.26x on average and up to 2.85x, with the largest gain occurring under overload. For diffusion image generation, Purlin reduces end-to-end latency by up to 1.13x.

## 1. 核心问题与整体含义

- **背景**：百亿至万亿参数 LLM 依赖分布式执行，scale-up 域（NVLink 域）已从 8 卡服务器扩展到 72 卡机架乃至 NVL576。张量并行、专家并行、序列并行等都依赖 AllReduce、AllGather(V)、ReduceScatter(V)、AllToAll(V) 等集合通信。
- **核心痛点**：现有集合通信实现把三件事**耦合**在一起：
  - **语义**（semantics）：MPI 定义的输入/输出契约；
  - **编排**（orchestration）：数据在*何处、何时*移动，即通信调度与跨 rank 同步；
  - **数据通路**（datapath）：数据*如何*移动，即用何种硬件机制完成拷贝/归约。
- **由此引出三个具体问题**：
  1. **可演进性与兼容性难以兼得**：采用新传输机制（如 Hopper TMA）需要改动数据通路之外的部分；某成熟库在 Hopper 发布 4 年后（2026）才支持 TMA-backed NVLink 传输；而 ParallelKittens 等新工作为追求极致性能只绑定 Hopper/Blackwell，放弃仍在部署的 Ampere。
  2. **缺乏“可推导性”（derivability）**：应用需要库未提供的集合通信（vLLM/SGLang/TensorRT-LLM 各自手写 AllReduce），但用 NVSHMEM/MSCCL++ 的设备端原语实现新集合通信仍需人工把语义翻译成编排。
  3. **定制化会牵动编排**：修改数据通路（如改归约顺序、融合通信与计算）往往要重写编排逻辑。
- **量化动机**：
  - 在 8×A100 上用 SGLang 服务 Qwen3.5-122B-A10B，通信占端到端延迟的 **24–32%**（p50 E2E / TPOT / TTFT），换用 Purlin 后延迟改善 1.23–1.25×。
  - 硬件侧：NVLink 单向带宽从 A100 300 GB/s → H200 450 GB/s → B200 900 GB/s，往返延迟约 2.2/2.1/2.8 μs，**BDP 从约 512 KiB 增至 2 MiB**，必须在飞数据量随之增长。
  - 资源侧：在 B200 上达到约 760 GB/s，Purlin 只需 16 个 SM，NCCL 设备 API 需 64 个 SM（4× 差距）。
- **整体含义**：作者主张“集合通信的语义与编排跨硬件代际是稳定的，只有搬数据的机制在变”，因此应把**不变的（where/when）**与**常变的（how）**分离，类似 IP、OS、编译器的分层思想，从而同时获得兼容性、可演进性、可推导性与可编程性。

## 2. 方法论

### 2.1 三层解耦架构（图 1）

| 层 | 内容 | 职责 |
|---|---|---|
| 顶层：语义 | 集合通信 = “一次 consume 操作 + 一对输入/输出布局”的命名，外加 codesign policy | 描述做什么 |
| 中层：SNAC | Stage, Notify, And Consume 共享编排协议 | 推导 where/when |
| 底层：Atom | 硬件相关的 `copy` / `reduce` 两个原语 | 实现 how |

### 2.2 布局（Layouts）与集合通信的可组合声明

- 三种布局（各有 V 变体，分区大小运行时给定）：
  - **packed**：一段连续贡献；
  - **scattered**：按 rank 索引的连续分区，分区 k 对应 rank k 的贡献/结果；
  - **transposed**：rank 索引分区的交换（表达 AllToAll）。
- 集合通信 = 布局变换：
  - `reduceScatter = SNAC<Atom, Policy, reduce, scattered, packed>`
  - `allGather = SNAC<Atom, Policy, copy, packed, scattered>`
  - `allToAll = SNAC<Atom, Policy, copy, scattered, transposed>`
  - **AllReduce = `compose<reduceScatter, allGather>`**（scattered→scattered），`compose<F,G>` 要求 F 的输出布局等于 G 的输入布局，且二者**融合为单个 GPU kernel**，G 原地消费 F 的中间结果，避免冗余访存与两次 kernel 启动。
  - 附录 A 进一步提出加 `Root` 编译期参数（producer/consumer/none）来表达 Broadcast/Scatter/Gather/Reduce 等 rooted 集合通信（`broadcast = compose<scatter, allGather>`，`reduce = compose<reduceScatter, gather>`）。

### 2.3 SNAC 编排协议

- **三段式流程**：
  1. **Stage**：各 rank 把应用缓冲区（无需注册）的数据本地拷贝到**已注册、可被对端访问的内部 staging buffer**；若应用直接提供 peer-accessible buffer 则可省略 staging（Purlin-ZS 变体）。
  2. **Notify**：staging 完成后以 **release 语义**通知其他 rank（packed 输入时通知所有 rank；scattered 输入时按 rank 顺序只通知 rank k）。
  3. **Consume**：每个 rank 以 **acquire 语义**等待通知，然后通过 `Atom::copy` / `Atom::reduce` 从远端拉取（pull）。packed 输出→跨所有 rank 归约；scattered/transposed 输出→按 rank 顺序拷贝摆放。
- **由布局推导依赖**：SNAC 是模板元程序，输入参数含布局，通过 `if constexpr` 在**编译期**决定通知对象、输出地址计算方式与消费方式，避免运行时分发进入关键路径。
- **CTA 特化 + 分块（chunking）**：把 N 个 CTA 分为 staging 组与 consuming 组；staging CTA 协作处理一个 chunk，完成后以 `acq_rel` 原子计数，最后一个 CTA 发布通知。AllReduce 有三组 CTA（staging、reducing、gathering），按 chunk 粒度流水化（图 5），最后一个 reducer 完成即向所有 rank 广播就绪。
- **延迟特化路径**：实验发现 **push（远端写）比 pull 延迟低至 1.98×**，而 pull 带宽高约 7%。因此吞吐路径用 pull，延迟路径用 push：把每 8 字节负载与 8 字节 flag（epoch）打包成 **16 字节 packet** 原子写入对端，消费者原子轮询 flag；代价是网络流量翻倍，故仅在延迟受限区间使用，交叉点由 codesign policy 决定。
- **确定性归约**：每个输出元素对应一个累加器，严格按 rank 升序累加（0→n−1），`E → FP32` 累加后再转回 `E`，保证可复现的固定归约顺序；另提供基于 `multimem.ld_reduce` 的 in-switch 归约作为**可选**路径（无顺序保证），在 8×H200、≥256 MiB 时比流水线软件归约快至 1.34×。

### 2.4 Atom 统一流水线

- 接口（Listing 3）：`copy(dst, src, bytes, workspace)` 与 `reduce<E, op>(dst, sources, bytes, n, workspace)`，`workspace` 指向 CTA 本地共享内存，`GPUArch` 支持按代特化，`Config` 描述流水线。
- 三阶段算法（Algorithm 2）：**prime**（填满 S 个 slot 的异步取数）→ **steady state**（等最老 stage、读入寄存器、向该 slot 异步预取、同时处理当前值）→ **drain**。copy 与 reduce 共享同一流水线，仅“处理”阶段不同（写目的 vs 更新累加器）。
- Ampere 及以上使用 `cp.async`；**刻意不用 TMA**，因为在 256 KiB–1 MiB 区间 cp.async 快约 10–12%，且 cp.async 走 LSU，与计算 kernel 的 TMA 单元不争用，利于融合场景。
- **BDP 导向的 codesign**：`Qcap = C · S · Bstage`（C 个 CTA、S 级流水、每级 Bstage 字节）。调深流水线可在固定 CTA 数下增加在飞字节。

### 2.5 实现

- CUDA C++20 **header-only** 库 + Python API；SNAC 及分区/packet/epoch 辅助共 2,480 行，codesign policy 598 行，Atom 各代实现 187/299/296/53 行，共享类型与工具 611 行；仅依赖 libcu++ 与 CUB。
- **循环 staging**：每 GPU 两个 256 MiB 吞吐 staging buffer 交替使用；超过容量时按 `256 MiB / chunkSize` 个 slot 轮转。
- **Epoch 记账**：每 CTA 维护 64 位持久 epoch，用**奇偶性选择双缓冲**，chunk 数取奇数以安全交替；epoch 同时作为通知值，从而消除跨 rank 的额外同步。
