## 摘要
大语言模型训练涉及在GPU流式多处理器（SM）上进行大规模计算，SM是GPU的主要计算单元。由于SM承载Tensor Core等专用加速器，其高效利用对训练效率至关重要。不幸的是，现有集合通信系统会与计算争用SM，因为它们消耗SM来执行通信相关的数据移动和同步操作。我们观察到，通信原则上可由DMA引擎驱动，从而消除通信对SM的参与。基于这一洞见，我们提出HOCCL，一个零SM集合通信框架，由三个组件组成：流管理器、点对点（P2P）执行器和集合调度器。流管理器保持与其他GPU内核的算子级时序顺序。P2P执行器实现零SM点对点通信，而集合调度器编排P2P传输以最大化带宽。实验表明，HOCCL保持接近峰值的通信性能，平均与当前最先进水平相差不超过3%，同时消除了通信对近10%的GPU总SM的占用。通过为计算释放SM资源，HOCCL将端到端训练吞吐量提升最高5%。

## Abstract
Large language model training involves massive computation on GPU streaming multiprocessors (SMs), the primary compute units of GPUs. Since SMs host specialized accelerators such as Tensor Cores, their efficient utilization is critical to training efficiency. Unfortunately, existing collective communication systems compete with computation for SMs, as they consume SMs for communication-related data movement and synchronization operations.   We observe that communication can, in principle, be driven by DMA engines, thereby eliminating SM involvement in communication. Based on this insight, we propose HOCCL, a zero-SM collective communication framework consisting of three components: a stream manager, a point-to-point (P2P) executor, and a collective scheduler. The stream manager preserves operator-level temporal ordering with other GPU kernels. The P2P executor enables zero-SM point-to-point communication, while the collective scheduler orchestrates P2P transfers to maximize bandwidth. Experiments show that HOCCL preserves near-peak communication performance, achieving within 3% of the state of the art on average, while eliminating communication occupancy on nearly 10% of total GPU SMs. By freeing SM resources for computation, HOCCL improves end-to-end training throughput by up to 5%.

## 1. 核心问题与研究动机

- **背景**：大语言模型训练的海量计算主要跑在 GPU 的流式多处理器（SM）上，SM 集成 Tensor Core 等专用加速单元，其利用率直接决定训练效率。
- **被忽视的低效**：现有集合通信系统（如 NCCL）把通信实现为 SM 上运行的 kernel，需要 SM 完成数据搬运（用户缓冲区 → RDMA 暂存缓冲区）和同步（通知 CPU proxy、轮询 CQ 等），因而与计算争抢 SM。
- **量化证据**：在 32 块 H800（每块 132 SM）上训练 GPT-6.7B 与 DeepSeek-V2-Lite，用 PyTorch Profiler 测得：TP/EP 峰值占用高（16/32 SM）但几乎不与计算重叠；PP 与 DP 为与计算重叠而设计，GPT-6.7B 下平均占用 11.2 个 SM（7.1+4.1），约占单卡 SM 总数的近 10%。作者定义"争用率"（计算活跃期间通信占用 SM 的时间加权比例），实验显示总争用率约 10% 时，前向、后向计算分别变慢 8.5% 和 7.7%。
- **现有替代方案的缺陷**：VCCL 通过运行时把用户缓冲区注册给 RNIC 来绕过 SM，但与 PyTorch expandable segments 等 VMM 机制不兼容（放弃后带来 >10% 显存碎片开销），且 Megatron-LM 中通信张量动态分配/释放导致反复注册，开销毫秒级、峰值可达数十毫秒，实测造成近 10% 端到端 slowdown。
- **核心洞见**：通信本可由 DMA 引擎（copy engine）驱动，从而彻底消除 SM 参与；DMA 引擎在训练中除首尾加载/落盘外长期闲置，资源上可行。

## 2. 方法论

### 2.1 总体架构

HOCCL 是零 SM 集合通信框架，基于 NCCL 扩展实现（核心运行时 3K+ 行 C++，PyTorch 后端约 1K 行），由三部分组成：

- **流管理器**（控制面）：维持通信与前后依赖 kernel 的 CUDA stream 时序语义。
- **点对点执行器**（数据面）：提供零 SM 的 P2P 传输原语，覆盖节点内与跨节点。
- **集合调度器**（调度面）：把多条 P2P 流编排为高带宽集合通信。

### 2.2 流管理器：CPU–GPU 握手同步

- 利用 CUDA 驱动低层原语 `cuStreamWriteValue32` / `cuStreamWaitValue32` 操作 **GPU 内存操作硬件**，使 GPU 无需 SM 即可读写 CPU 内存中的标志位。
- 每条 GPU stream 在 CPU 内存维护 `start_flag` 与 `finish_flag`：
  - **启动路径**：stream 写入 `START_VALUE` → CPU proxy 轮询并消费、清零 → stream 等待清零作为确认后继续；
  - **完成路径**：CPU 写 `FINISH_VALUE` 到 `end_flag` → stream 等待该值 → stream 清零作为最终确认。
  - 双向握手使每次状态转换显式可见、标志可安全复用，从而在无 SM 通信 kernel 的情况下保持 stream 顺序语义。
- **标志池 + 缓冲区状态机**：每个暂存 chunk 关联一个共享标志，编码 `idle` / `DMA copying` / `RNIC in progress` 三态，统一协调 CPU 侧 RNIC 操作与 GPU 侧 DMA 任务两条异步路径。

### 2.3 零 SM 点对点执行器

**跨节点通信**（图 5a）：

- **对称 GPU 缓冲区**：DMA 引擎不能直接做 RNIC 传输，因此在同一 PCIe switch 下的"对称 GPU"上为每块 GPU 分配收/发两个 RDMA 暂存缓冲区；本地 GPU 与对称 peer 到 RNIC 距离相同，不引入额外路径开销。
- **DMA–RNIC chunk 流水**：暂存区组织为 buffer pool，发送侧 RNIC 发送就绪缓冲的同时 DMA 填充空闲缓冲，接收侧 RNIC 写入的同时 DMA 排空到用户缓冲，以此摊薄 DMA 启动开销与额外 staging 拷贝。
- **多 QP 并行**：每条连接使用多个 RDMA 队列对（2 或 4 个）条带化 chunk，加深流水，隐藏 CPU–GPU 控制延迟与 DMA 启动延迟。

**节点内通信**（图 5b）：

- **运行时 IPC-handle 交换**：基于 POSIX 信号量 + 共享内存，接收侧 proxy 导出 `cudaIpcMemHandle` 并发布，发送侧运行时打开并解析目的地址后直接 DMA 写入，避免 staging 拷贝，也避免要求通信前地址已知。
- **CPU 侧跨进程同步**：DMA 写完成后发送侧 proxy 投递信号量，接收侧等待并标记完成，再由流管理器通知对应 GPU stream。

### 2.4 集合调度器

- **流量矩阵抽象**：用户集合描述 → 原始流量矩阵 `C`（逻辑流 f1…f12）→ 扩展为 HOCCL 流量矩阵 `T`。跨节点逻辑流 fm 被实现为三段：发送侧 NVLink 转发拷贝 f′m + RDMA 传输 fm + 接收侧转发拷贝 f″m；即 `T[u,v] = C[u,v] + Au + Bv`（NVLink 域且 v=ū 时），否则 `T[u,v]=C[u,v]`，其中 Au、Bv 分别为该 GPU 发出/接收的跨节点流转发量之和。
- **拓扑感知流调度**：把 T 分解为阶段矩阵 T1…Tn，需满足三条件：
  1. **完整性**：Σ Ts = T（逐元素）；
  2. **每阶段度约束**：每个 GPU 每阶段至多一条出向、一条入向 RDMA 流，避免单卡/单 NIC 成为瓶颈；
  3. **跨域平衡**：阶段时长由最慢域决定，域 d 的工作量 Lsd = 该域内最大流大小，阶段时间 τs = max_d (Lsd/Bd)，优化目标为 min Στs。
- **Birkhoff 式分解算法**：先在各 NVLink 域内预分解本地流量；循环从残差矩阵中抽取无竞争的 RDMA 匹配、移入当前阶段并扣除，补上相应转发拷贝，再用剩余 NVLink 空余填充本地匹配分量，直至残差清空。
- **流大小感知的 chunk 调度**：单个 DMA 引擎串行执行，按流大小比例分配 DMA 服务时间片、加权交织各流 chunk，避免大流垄断导致转发积压与长尾，使同阶段各流近似同时完成。

## 6. 主要结论与发现

- **通信性能接近 SOTA**：平均与最先进水平差距在 3% 以内。节点内 P2P 1 GB 时达 192.2 GB/s（比 NCCL-8SM 高 23%）；跨节点 P2P 1 GB 时 48.8 GB/s，接近 50 GB/s 链路极限；16-GPU AllGather 48.2 GB/s，与 NCCL-4SM/8SM（47.9/48.3）相当；8-GPU All-to-All 191.4 GB/s，超 NCCL-8SM 24%；16-GPU All-to-All 57.7 GB/s，但低于 NCCL-8SM 的 67.7 GB/s（差 17%）。
- **小消息劣势**：2 MB 时节点内 19.6 GB/s vs NCCL-8SM 41.0 GB/s，源于 DMA 启动延迟（约为 SM 拷贝的 5 倍）与流水建立成本。
- **零 SM 占用**：通信不再占用 SM，释放近 10% 的总 GPU SM 资源。
- **端到端收益**：6.7B 上 214.8 vs NCCL 209.8 TFLOP/s（+2.4%），VCCL 仅 190.9（−9.0%）；32B 上 491.7 vs 467.8（+5.1%），并优于 VCCL 的 478.7（+2.7%），且波动更小（486.8–495.8 vs VCCL 461.6–491.4）。
- **计算时间直接缩短**：前向降 1.5%（mbs=1）与 5.4%（mbs=2），后向降 6.4% 与 8.1%，把吞吐提升归因于 SM 释放。
- **CPU 不成为瓶颈**：HOCCL 的 host 侧 launch 开销更高（跨节点从 11.8

μs 升至数十 μs 量级，节点内亦有相近幅度的增加），但由于控制面工作全部下沉到 CPU proxy 线程并与 DMA/RNIC 传输重叠，CPU slack 采样显示 host 侧仍保有大量空闲时间，未进入训练关键路径，因此更高的 launch 开销没有转化为端到端损失。
- **对 VCCL 路线的实证反驳**：VCCL 在 6.7B 上反而比默认 NCCL 慢 9.0%，说明"用户缓冲区直接注册给 RNIC"的方案在 PyTorch VMM + 动态分配的现实训练栈中，注册/注销开销足以吞噬零 SM 带来的收益；HOCCL 用 staging 缓冲区回避注册问题，代价是额外一次 DMA 拷贝，但该拷贝被 DMA–RNIC chunk 流水完全重叠，未体现在带宽曲线上。
- **总体判断**：论文的核心命题——"集合通信可以由长期闲置的 DMA 引擎承担，从而在不牺牲带宽的前提下把 SM 全部还给计算"——在 32 卡 H800 平台上得到了定量支持；但其收益量级（2.4%–5.1% 端到端）与"SM 争用率约 10%"的背景测量是同一数量级的因果闭环，而非数量级跃升。

## 7. 局限与值得追问之处

- **对称缓冲区假设的普适性**：跨节点路径要求同一 PCIe switch 下存在"对称 GPU"以放置收发暂存区，这一前提在 NVLink 全互联节点、PCIe switch 拓扑不规则或 GPU–NIC 非一一映射的机器上是否成立、退化后损失多少带宽，论文未展开。
- **额外显存开销未量化**：buffer pool、多 QP 条带化与三段式转发（f′m/fm/f″m）都需要额外显存与 NVLink 带宽；论文报告了 SM 与时间收益，但未给出显存占用增量，也未讨论转发拷贝对 NVLink 带宽的挤占在更大规模下是否会成为新瓶颈。
- **小消息与跨节点 All-to-All 的短板**：2 MB 时节点内带宽不到 NCCL-8SM 的一半，跨节点 All-to-All 低于 NCCL-8SM 17%，说明 DMA 启动延迟与流水建立成本在短消息、多对多模式下仍是硬约束；而真实训练中 PP 的 send/recv 恰以中小消息为主，这一短板的实际影响需要更细的粒度分析。
- **依赖低层驱动原语**：`cuStreamWriteValue32`/`cuStreamWaitValue32` 与 `cudaIpcMemHandle` 的运行时交换属于贴近硬件的实现，跨 CUDA 版本、跨驱动、跨厂商（如 ROCm）的可移植性与稳定性风险未被讨论。
- **覆盖面**：端到端只加速 PP send/recv 与 DP AllGather，TP 的 AllReduce/ReduceScatter、EP 的 All-to-All 仍回退 NCCL；而背景测量恰恰显示 TP/EP 的峰值 SM 占用最高（16/32 SM），即收益最大的部分尚未被覆盖，这使 2.4%–5.1% 的端到端数字更像是下界而非上限。
- **评估严谨性**：单一硬件平台、两个模型、缺少组件消融与多次运行的方差统计，也未验证收敛性与数值等价性；"吞吐提升归因于 SM 释放"的因果链虽有计算时间分解佐证，但仍属相关性证据，缺少"固定 SM 预算下对照"的直接实验。

## 8. 启示与可推广方向

- **资源视角的转换**：论文最有价值的方法论不在于具体工程，而在于把"通信必须占用 SM"当作可质疑的默认假设，转而盘点集群中真正闲置的硬件资源（DMA 引擎、NIC 片上缓存、PCIe 带宽），这类"闲置资源置换稀缺资源"的思路可迁移到 checkpoint、数据加载、KV cache 换出等场景。
- **控制面与数据面分离的范式**：CPU 负责编排与握手、专用引擎负责搬运、SM 只做计算，这一分工与近年 GPU-initiated communication、DPU/IPU 卸载、NVLink SHARP 等方向在理念上同源，区别在于 HOCCL 不要求更换硬件或编程模型。
- **拓扑感知调度的可复用性**：把集合通信抽象为流量矩阵、再按"每阶段每卡至多一条出/入 RDMA 流"的度约束做 Birkhoff 式分解，是一个与具体传输引擎无关的组合优化框架，可直接用于多 NIC rail-optimized 拓扑或异构链路（NVLink + IB + PCIe）下的调度。
- **对系统栈协同的提醒**：VCCL 的失败说明通信优化不能脱离内存管理栈（VMM、expandable segments、动态分配）单独设计；任何"零拷贝"承诺都必须回答"缓冲区生命周期由谁保证"。

## 9. 一句话总结

HOCCL 通过"CPU 侧双向握手维持 stream 语义 + DMA 引擎承担数据搬运 + 拓扑感知流量矩阵调度"三件套，把集合通信的 SM 占用降为零，在 32 卡 H800 上以 ≤3% 的带宽代价换取近 10% 的 SM 资源与 2.4%–5.1% 的端到端吞吐提升，是一次假设大胆、证据链完整但覆盖面仍待扩展的系统性探索。
