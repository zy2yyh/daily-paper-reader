Abstract —Simulation of HPC applications is an essential tool for analyzing system design trade-offs and enabling effective hardware–software co-design. As modern supercomputers in-creasingly rely on GPU acceleration, MPI implementations have evolved to support GPU-aware communication, enabling direct GPU data transfers. Modeling these mechanisms is therefore critical for simulating HPC applications on current systems. In this paper, we introduce Orrery, an interposition layer built on SimGrid’s SMPI to model GPU-aware MPI communication using existing collective implementations and flow-based simulation. Orrery intercepts GPU memory allocations, kernel launches, data transfers, and MPI operations, and models their execution in SimGrid according to target system specifications, enabling simu-lation without requiring physical GPUs. We validate Orrery using CUDA-aware MPI microbenchmarks and a Jacobi solver on up to 32 nodes of the MUSICA supercomputer and demonstrate that it reproduces key GPU-aware MPI mechanisms. 

Index Terms —GPU-aware MPI, CUDA-aware MPI, Simula-tion, Performance Modeling, SimGrid, Collective Communica-tion, GPU Communication. 

I. I NTRODUCTION 

GPUs are widely used in modern HPC systems, and, e.g., in the latest TOP500 ranking (June 2026) [1], four of the top five supercomputers are equipped with GPUs. Consequently, MPI implementations have evolved to support GPU-aware commu-nication, enabling direct interaction between GPU memory and distributed communication mechanisms. As GPU-accelerated systems become increasingly prevalent, accurate performance modeling and simulation of these architectures are essential for analyzing, understanding, and optimizing HPC applications, as well as for guiding the design of future systems. Simulators leveraging novel techniques and tools play a critical role in evaluating the performance and scalability of applications and algorithms: Simulation enables evaluation of system configurations and application designs, allowing system architects and applica-tion developers to rapidly evaluate algorithm and hardware scalability and compare alternative approaches before costly deployments on large-scale systems. Simulating modern GPU-accelerated HPC applications re-quires capturing and modeling kernel executions, data paths and data movements, as well as the support for GPU-aware communication mechanisms, often hidden behind the MPI interface. In particular, modeling GPU-aware MPI, empowered by peer-to-peer GPU communications [2] that is often used in modern GPU-accelerated systems, becomes increasingly important for simulating many scientific applications. Sim-Grid [3], [4] provides a strong foundation for this goal through its execution-driven model, detailed network abstraction, and SMPI support for simulating MPI applications; however, SMPI has been designed for CPU-based MPI execution and lacks native support for representing GPU memory management, GPU kernel execution, and GPU-aware MPI communication. This work addresses this gap by extending SimGrid with GPU-aware communication capabilities, in particular target-ing a CUDA-aware platform with GPUDirect RDMA [5] transports. We introduce Orrery 1, an interposition layer that enables the online simulation of CUDA-aware MPI appli-cations. Without modifying SimGrid, Orrery intercepts and models GPU memory management operations like allocation and data transfer calls, kernel launches, and GPU-aware MPI communications, allowing for leveraging existing SimGrid and SMPI simulation engines for GPU-enabled HPC applications. The main contributions of this work are as follows: 

C1: We present Orrery, an interposition layer built on the SMPI, and its first implementation, the first GPU-aware extension in SimGrid ecosystem. that enables online simulation of CUDA-aware MPI applications. 

C2: We introduce two execution modes enabling applications to be simulated regardless of whether GPU devices are physically present on the simulation platform (Twin mode) or not (Skeleton mode).

SimGrid: SimGrid is an open-source framework for simu-lating distributed systems through analytical models of com-putation, communication, and I/O over user-defined virtual platforms. Its SMPI module enables execution-driven simu-lation of MPI applications by redirecting MPI operations to SimGrid’s implementation, where each rank is represented as a lightweight simulation actor. Communication operations are simulated using SimGrid’s flow-level network models and SMPI’s implementations of the collective algorithms of MPI libraries, such as the ones implemented in Open MPI [6], while computations are represented by either native kernel execution and scaling their measured durations to the simulated platform, or by replacing them with virtual delays (advancing per rank virtual clocks). This approach enables lightweight and scalable simulation of MPI applications on a single machine without requiring access to the target system [6]. 

GPU-aware MPI : Unlike traditional MPI, GPU-aware MPI accepts device pointers as communication buffers, allowing data to remain on the GPU unless staging through host memory is enabled [2]. GPU-aware MPI implementations typically determine the memory type of communication buffers and select an appro-priate data path, including peer-to-peer transfers over PCIe or NVLink within a node, GPUDirect RDMA across nodes [5], or staged transfers through pinned host memory when direct GPU communication is unavailable. 

Related Work : Prior work has explored simulation approaches for large-scale HPC systems, primarily focusing on CPU-based communication and network behavior. Trace-driven simulators capture, parse, and replay application executions under dif-ferent system configurations; for example, LogGOPSim [7] and PHANTOM [8] provide MPI-oriented communication models, while ATLAHS [9] enables evaluation of distributed workloads through a common representation and multiple simulation backends. However, trace-based approaches capture only a specific execution instance, requiring new traces for different configurations and limiting scalability studies [9], [10], while trace collection and storage can become costly at large scale [9], [11]. Execution-driven simulators, such as SimGrid/SMPI [6] and xSim [12], address these limitations by executing applications against a modeled platform, while SST/macro [13] and BigSim [14] combine both approaches. With the rise of GPU-accelerated systems, simulators such as ASTRA-sim [15]–[17] and SimAI [18] have extended sim-ulation toward distributed AI workloads, through specialized GPU communication tools such as NCCL [19]. None of these approaches support GPU-aware MPI: execution-driven simu-lators lack device-memory awareness, while AI-oriented sim-ulators primarily target NCCL-based communications rather than MPI. III. S IMULATING GPU-AWARE MPI WITH ORRERY 

Figure 1 presents the overall architectural design of Orrery. Orrery acts as an interposition layer that interfaces with SMPI to support GPU-aware MPI applications without modifying the underlying SimGrid framework. An application leveraging a GPU-aware MPI 1⃝ runs unmodified, while Orrery 2⃝

intercepts relevant GPU (CUDA) runtime and MPI calls. GPU memory allocations, data transfers, kernel executions, and communication operations are captured and modeled as a target machine description representing the bandwidth and la-tencies of operations and the data paths 3⃝. This design allows using the existing SimGrid simulation cores: The resulting execution costs are charged to each rank’s virtual clock within SimGrid 4⃝, which continues to provide the underlying process scheduling and network simulation. 

A. Orrery Interposition 

SMPI’s standard build process targets host-based MPI appli-cations and cannot compile or link device code. Orrery extends the build process by using the vendor toolchain ( nvcc in our prototype) for device code compilation and final linking while retaining SMPI’s MPI interface. The interposition layer and cost model (Sec. III-B) are compiled with the application into a shared object loaded by smpirun , making interception a link-time property rather than a runtime preload mechanism. To intercept CUDA runtime operations, Orrery provides CUDA wrappers bound at the application binary interface (ABI): link-time symbol binding redirects calls such as cudaMalloc 

to Orrery without parsing or transforming the source. MPI interception leverages the standard MPI Profiling Interface (PMPI) mechanism [20]: Orrery provides weak MPI wrappers, while PMPI_* symbols are resolved by SMPI. D. Execution Modes 

Orrery provides two execution modes, following SMPI’s treatment of computation phases. In both modes, intercepted operations are evaluated by the cost model and their durations are added to the rank’s virtual clock. SimGrid handles schedul-ing and contention: Orrery determines the operation duration, while SimGrid determines its execution. The modes differ only in how wrappers handle operations before charging: 

Skeleton mode does not require GPUs: memory allocations use an internal registry, and kernels and data transfers are modeled with cost models. However, the device buffers contain no output, and no kernel is launched. This mode uses all Equations 1-3 for modeling. 

Twin mode requires a GPU for GPU kernel execution (does not use Equation 3), and forwards each call to the CUDA runtime and charges the measured duration. This is done by leveraging -Bsymbolic to resolve the name to the wrapper; the real entry point comes from dlsym(RTLD_NEXT) .IV. E XPERIMENTAL RESULTS 

A. Experimental Setup 

Reference measurements are collected on 32 nodes of the MUSICA supercomputer, each equipped with four fully con-nected NVIDIA H100 GPUs via NVLink 4.0 and connected by 200 Gbit/s InfiniBand. The system runs Open MPI 4.1.6 with UCX 1.15, CUDA support, and GPUDirect RDMA. Simulations use skeleton mode on a workstation with an 4-core Intel Xeon W-2125 (4.0 GHz), 32 GB memory, and a 5 GB Quadro P2000 GPU, running SimGrid 4.1.1.

Figure 4 shows a Jacobi solver [26], simulated in skeleton mode with every kernel launch modeled using Eq. 3. On different number of nodes (Fig. 4a), the relative error of the simulation is at most 27%, and we can see how increasing the number of nodes in the simulator to 256 improves the performance. The inset highlights the communication phases: 0.35 s measured versus 0.14 s simulated, with halo exchange undercharged ( −81% )and norm calculation overcharged ( +16% ). V. D ISCUSSION 

The errors in the simulation arise in part from calibration mismatches: the calibration relies on isolated two-GPU device-buffer measurements, whereas real applications involve dif-ferent buffer types and communication patterns. In addition, collective operations introduce concurrent transfers that are not captured by the current calibration benchmarks and probes (listed in Table I). Part of the error is also structural: the cost model is built from simple latency–bandwidth terms in the style of Hockney [21] and LogGP [22], which abstract away effects such as protocol switches, memory registration, and contention among concurrent transfers, so a residual error may remain even with well-tuned parameters. Improving accuracy requires independent measurements for host-buffer transfers and concurrent communication scenarios, as well as accounting for network and memory contention. Two limitations remain in our current prototype: First, skeleton node relies on a single measured kernel rate, which is sufficient for memory-bound workloads but cannot distinguish computation and memory effects or generalize across kernels and architectures. Second, Orrery currently models operations sequentially, so it cannot capture computation-communication overlap in asynchronous applications. VI. C ONCLUSION AND FUTURE DIRECTIONS 

We introduced Orrery, an interposition layer that extends SimGrid’s SMPI to GPU-aware MPI applications, modifying neither the simulator nor the application code. It captures GPU runtime calls (e.g., CUDA calls) and charges each from a calibrated cost model, exposing the device-side cost of a GPU-aware MPI implementation to the simulation framework. Several extensions can broaden Orrery’s applicability. Start-ing with validation on full applications. The interception approach can be extended beyond CUDA to other runtimes such as HIP and SYCL, which would allow validating the cost model on GPUs from other vendors, while additional and automated calibration [25] can improve model accuracy. Twin mode enables validation across real platforms, and the ma-chine description allows exploration of future GPU systems, topologies, and extending previous MPI algorithm selection studies to be GPU-aware [27]. Such modeling can also eval-uate emerging approaches, such as in-network computing, as in [28]. As the GPU communication stack moves further off the host, we envision Orrery setting the foundations for modeling GPU-aware communication based on GPUDirect RDMA in the well-established community-driven SimGrid simulator to better evaluate machines, libraries, and algorithms, including those that do not yet exist.
