# SigmaTrace: Library-Agnostic Observability for CPU/GPU-Initiated RDMA Communication 

Javid Baydamirli

Abstract —RDMA networking enables low-latency, high-band-width communication on large systems. Despite its adoption, however, observability is lacking. Existing tools target specific communication libraries or only report aggregated data, missing per-operation behavior. The gap is widest for GPU-initiated networking, whose in-kernel RDMA operations are invisible to the host. We present SIGMA TRACE , a library-agnostic RDMA profiling framework providing fine-grained, per-operation visibility for CPU and GPU-initiated networking. It traces operations at the 

libibverbs /mlx5dv layers, the common denominator beneath communication libraries on InfiniBand and RoCE, and employs a low-overhead memory interposition technique that, to our knowledge, gives the first observability into GPU-initiated RDMA without source patching or binary instrumentation. Host-side tracing adds 1.3% overhead on NCCL AllReduce at 128 GPUs and under 2% on RCCL at 1024 GPUs. On a persistent-kernel BFS and Mixture-of-Experts inference, SIGMA TRACE 

exposes an in-kernel barrier spread and 2.13 × inter-node traffic skew invisible to existing profilers. 

Index Terms —GPU-initiated networking, High performance Computing, Network interfaces, Performance evaluation, Remote Direct Memory Access (RDMA) 

I. I NTRODUCTION 

Communication overhead is a major consideration for scalability and efficiency in AI training and inference, as well as scientific computing workloads [1]–[3]. To better meet performance-critical data movement demands of modern workloads, large-scale clusters now ubiquitously employ high-speed and low-latency Remote Direct Memory Access (RDMA) networking. At the software level, RDMA communication has seen wide adoption in libraries including NCCL [4], NVSHMEM [5], MPI, UCX [6], and many of their derivatives, dominating the high-performance computing landscape. Significant effort has also been directed at bringing native networking to GPUs. Traditionally, CPU threads managed network buffers and operations on behalf of GPUs. GPUDirect RDMA [7] moved the data path onto devices, allowing NICs

Later, GPUDirect Async (IBGDA) [8] moved the control path onto devices as well, enabling GPU threads to construct RDMA messages in device memory, write to NIC doorbells to initiate communication, and poll for completion without CPU involvement. This paradigm of putting the devices in control of communication can reduce end-to-end latency greatly while allowing higher levels of computation and communication overlap [9]–[13]. GPU-initiated networking has been adopted by first-party libraries [4], [5] and is increasingly specialized for latency-sensitive workloads such as Mixture-of-Experts (MoE) routing: DeepEP V2 [14] uses NCCL’s device-side API to minimize all-to-all dispatch latency across hundreds of expert-parallel ranks, and several communication libraries have since built on it [15]–[17]. Despite the growing adoption of both CPU and GPU-initiated RDMA, tooling for observability, performance engineering, and communication debugging has not kept pace. Existing profiling and tracing tools largely focus on a single high-level layer in the communication stack, missing RDMA-level information, and remaining entirely blind to GPU-initiated operations: GPU-initiated RDMA is opaque to the host and consists of loads and stores that are indistinguishable from the many other memory operations occurring within a kernel. Unlike its CPU-side counterpart, there are no API boundaries or software events that can be used as observability points. Tools like Mycroft [18], NCCL Inspector [19], and NPKit [20] that instrument GPU communication libraries trace the host-side proxy threads and API calls but stop squarely at the kernel launch. On the other hand, binary instrumentation-based tools like Snoopie [21] incur high overheads due to assembly level injection across all memory operations [22]. Vendor profilers like NVIDIA’s Nsight Systems [23] and AMD’s ROCm Systems Profiler [24] provide system-level aggregate NIC counters, but cannot attribute metrics to an individual kernel, GPU, or even process, and offer little visibility into the actual RDMA operations being performed. As a result, the most performance-critical operations are paradoxically the least visible. To address the observability gaps, we present S IGMA TRACE ,an RDMA profiling framework that provides fine-grained, per-operation visibility into the full communication stack for both CPU and GPU-initiated networking. Our approach relies on one arXiv:2610.24328v1 [cs.DC] 16 Oct 2026 observation: while GPU-initiated RDMA bypasses traditional software interception points such as API calls, it cannot bypass the hardware interface between the GPU and the NIC. Even with fully GPU-native networking, where all communication buffers reside entirely within device memory and data moves through hardware-level DMA without the CPU on the path, every RDMA operation is ultimately initiated by a PCIe write. The write is done from within GPU kernels to a NIC’s doorbell register, which is exposed in its PCIe memory-mapped I/O (MMIO) Base Address Register (BAR) and memory-mapped into the application’s address space. This gives us a single observable point below all communication libraries and opaque memory instructions, on a data path accessible to the CPU. We exploit this point and selectively replace the doorbell pages that would be mapped into GPU address space—NIC 

User Access Region (UAR) pages—with pinned CPU memory through hijacks at the mlx5 direct verbs and CUDA driver levels, redirecting doorbell writes without modifying the target application. When the GPU rings the doorbell to initiate a transfer, our polling thread captures it first, records the RDMA metadata associated with it, and forwards the request to the real NIC for execution. To our knowledge, S IGMA TRACE is the first tool to both enable observability into GPU-initiated RDMA operations, and to employ GPU-level memory interposition for profiling without binary instrumentation. Our contributions are as follows:  

> •

The first observability solution for true GPU-initiated networking : We capture precise doorbell timing and RDMA work queue content, invisible to all existing tools.

> •

We evaluate S IGMA TRACE on up to 128 nodes, demonstrating as little as 1.3% overhead on NCCL AllReduce on 128 GPUs across 32 nodes and under 2% on RCCL at 1024 GPUs across 128 nodes. We further characterize the overhead of the memory-hijack mechanism with microbenchmarks and present two case studies: a distributed persistent-kernel BFS traversal, where SIGMA TRACE reveals early per-level graph load imbalance and straggler barriers, and a Mixture-of-Experts inference workload, where S IGMA TRACE exposes inter-node traffic skew across data-parallel ranks. RDMA communication is organized around sets of queues. In the InfiniBand verbs model, endpoints are Queue Pairs (QPs) ,each consisting of a Send Queue (SQ) and a Receive Queue (RQ) . To issue an RDMA operation, the application constructs a Work Queue Element (WQE) in SQ memory describing the operation type ( WRITE , READ ), local and remote buffer identifiers, and the transfer size. The application then rings the NIC doorbell through a write to its User Access Region (UAR) , a register page exposed in the NIC’s PCIe BAR and memory-mapped into the process address space. A doorbell write may batch multiple WQEs for asynchronous execution, after which the NIC posts Completion Queue Entries (CQE) to the Completion Queue (CQ) . Data movement other than the doorbell takes place through DMA engines within the NIC and PCIe subsystem. 

A. GPUDirect RDMA 

Hardware prerequisites for RDMA networking—PCIe BAR access and DMA capability—are present on modern GPUs, which are themselves both DMA peers and PCIe endpoints. This means that all RDMA queues and memory buffers described above can reside in GPU memory and be accessed by NIC hardware transparently. Furthermore, the NIC’s doorbell registers, exposed on its PCIe BAR, can be mapped into user-space virtual memory and subsequently registered with the GPU driver for in-kernel access, allowing GPU threads to construct WQEs in device memory and notify the NIC via stores to the mapped doorbell address. This mechanism underlies GPUDirect RDMA [7] and GPUDirect Async [8], which enable GPU-initiated networking (GIN) [26]. This communication path is used by NVSHMEM’s IBGDA transport [5] and the DOCA GPUNetIO SDK [27], used by NCCL’s recently introduced GDAKI backend [26]. On AMD systems, rocSHMEM [28] implements an analogous GPU-initiated path using GDA transports over Mellanox NICs, while RCCL [29] currently relies on CPU proxy threads for network operations. 

B. Motivation and Gaps in Observability 

Consider an application performing a remote put operation (Figure 1). Internally, GPU threads construct several RDMA 

WRITE WQEs of varying sizes on their local memory to addresses on remote peers and write to NIC doorbell registers using global memory operations ( STG.E.STRONG.SYS or 

STG.E.STRONG.GPU in CUDA SASS). Depending on the size of the transfer, the number of peers, and the network topology, a single kernel invocation may issue hundreds of such operations across several QPs connected to many remote nodes and GPUs. Because this communication path is reduced to ordinary memory operations on mapped address ranges, GPU-initiated RDMA is largely invisible to conventional profiling tools. Nsight Systems shows such kernels as opaque timeline blocks and reports only aggregate NIC statistics without per-kernel or per-GPU attribution. Similarly, tools such as Mycroft [18], NPKit [20], ucTrace [30], and Aegis [31] instrument host-side communication and therefore miss in-kernel operations that bypass the host entirely. At this stage, extracting runtime network information from the application is impossible without extensive source code modifications or binary patching. Performance pathologies caused by communication imbalance across peers and QPs, congestion reflected in doorbell register activity, bandwidth underutilization across kernels, and other correctness bugs are reflected in doorbell register writes and WQE contents that no existing tool currently targets. III. S YSTEM DESIGN 

A. Design Goals and Challenges 

We define and outline the following design goals for SIGMA TRACE and the challenges they introduce:  

> •

Capturing all RDMA operations , both CPU and GPU-initiated. The tool must record precise doorbell timings, extract WQE metadata, and correlate events across threads, processes, and network nodes.  

> •

Maintaining low overhead while remaining non-intrusive to the communication flow. Since RDMA applications often issue and poll for fine-grained operations, the tool must handle high-frequency traces efficiently, scale reasonably alongside the application, and consolidate data efficiently on large systems.  

> •

Remaining communication library agnostic without requiring source modifications or recompilation. Since communication routines may traverse multiple software layers and internal buffers, the tool must gather sufficient information independent of library specifics. 

B. Architecture Overview 

SIGMA TRACE is implemented as a two-part architecture that decouples runtime capture and offline reconstruction. The 

Profiler on the hot path captures fine-grained RDMA activity while keeping the overhead low, and the Correlator parses and consolidates the collected data post-mortem. The Profiler intercepts communication activity at selected software layers, including host-side RDMA and middleware calls, mlx5dv state creation, and CUDA driver calls required for GPU doorbell interposition. We keep the Profiler as light as possible with minimal state tracking and only record data points available to a single thread during application execution. Subsequently, the Correlator merges per-thread traces and metadata, normalizes timestamps, reconstructs queue-pair connectivity, associates doorbells with WQEs, and matches communication activity across processes and nodes. This split allows us to minimize the overhead of the tool, as Profiler 

threads perform the minimal amount of work to record traces without synchronizing or communicating among one another. 

C. Selective Tracing 

The Profiler is composed of a set of modular event providers implemented as LD_PRELOAD shims that can be enabled selectively at runtime. This allows users to pick and choose injection targets and reduce the overhead of the tool; for example, a user may choose to omit the libibverbs layer and only collect UCX data at startup without further runtime overhead. Within the selected libraries, S IGMA TRACE supports three trace modes:  

> •

Aggregate : Collects only total communication volume with source and destination markers, using thread-local in-memory aggregation with no timestamping for minimal overhead and file I/O.  

> •

Simple (Default) : Records a reduced set of traces, omit-ting high-frequency operations such as ibv_poll_cq 

completions. This mode allows a higher-level visualization of the network flow at low overhead.  

> •

Full : Records all supported events, including per-request operations such as nested ibv_post_send work re-quests. This mode provides the highest fidelity at the cost of increased I/O pressure and a larger hit to application performance, and is meant for short, targeted debugging tasks rather than production runs. We note that the architecture of S IGMA TRACE fully disables trace collection for omitted events, meaning no overhead is incurred for calls that are not traced. IV. B. CUDA Driver Interception 

To transparently interpose UAR memory without changing pointer semantics and consequently distorting application execution, S IGMA TRACE must modify the behavior of the CUDA driver API, in particular, host memory management functions. While CUDA provides tooling for observability into the driver API through CUPTI [32] and the Sanitizer API [33], it is currently not possible to inject custom code during execution or alter return values of the runtime methods. Moreover, the 

LD_PRELOAD and dlsym interposition techniques described earlier are not sufficient for the CUDA driver API, since most symbols are resolved through internal undocumented dispatch tables. To address this, we intercept two CUDA driver entry points used to bootstrap symbol resolution: cuGetProcAddress 

and cuGetExportTable . These interfaces expose dispatch tables that are later used to resolve additional CUDA driver and runtime symbols. We instrument the tables by inspecting and saving the original function pointers and replacing them with pointers to our own wrappers. This allows us to selectively inject our instrumentation while preserving the original CUDA driver behavior for other calls. 

C. Doorbell State Reconstruction 

To interpret doorbell writes, S IGMA TRACE must know the QP configuration, SQ memory layout, and endpoint information associated with each doorbell at the time it is fired. We extract this data by intercepting mlx5dv setup calls on the host side during transport initialization. Specifically, we track the following runtime state: 

UAR lifecycle. We record UAR allocations done through 

mlx5dv_devx_alloc_uar with their register address, page identifier and the associated NIC device context. On a call to mlx5dv_devx_free_uar with the same page ID and register address, the tracking state is cleared. 

UMEM registration. mlx5dv_devx_umem_reg regis-ters a contiguous memory region (possibly GPU memory allocated with cuMemAlloc or equivalent) into the NIC’s address space. S IGMA TRACE queries cudaPointerGet Attributes on the registered address to determine whether the memory is GPU-resident, or host-accessible. For GPU-resident memory, we record a mapping from the registered-memory ID to the memory address, GPU device ID, memory type, and CUDA context. This mapping allows us to determine which GPU owns the send queue buffer when a queue pair referencing the memory ID is created. 

QP creation . Following the UAR allocation and UMEM registration, a queue pair is created through mlx5dv_devx_ obj_create with opcode MLX5_CMD_OP_CREATE_QP ,referencing the aforementioned UAR and UMEM. We extract the address, capacity, and byte offsets of the SQ, the service type of the transport, and the QP number from the command mailbox.

V. GPU D OORBELL HIJACK AND WQE R ECOVERY 

A. Memory Hijack 

Our doorbell tracking mechanism involves selectively re-placing memory-mapped NIC UAR pages with CPU-visible memory pages to intercept doorbell writes without source code modifications or binary instrumentation. To achieve this, we identify and exploit the following three-step sequence for setting up GPU-initiated networking: 1) UAR Allocation : The target application calls mlx5dv_ devx_alloc_uar to allocate a NIC user access region. The allocated structure contains a host-accessible virtual address space pointer to the doorbell register mapped over the NIC’s PCIe BAR. 2) CUDA Host Memory Registration : The target application then calls cuMemHostRegister on the register address to make the mapped I/O range accessible to CUDA kernels. 3) Device Pointer Resolution : The application calls cu MemHostGetDevicePointer to obtain a GPU-side pointer to the register address. This pointer is written to by GPU threads to ring doorbells. We intercept all three steps above to transparently replace the UAR register space as well as device-side pointers. At steps 1 and 2, we simply record and mark the address ranges as possible candidates for replacement. At step 3, we allocate a fake 4KB page in pinned host memory and return a device-side pointer to it instead. From the GPU’s perspective, stores to pinned host memory and to the registered UAR mapping behave identically—both are uncached posted writes that cross PCIe—so the profiled application transparently receives a valid device-side pointer with the same store semantics as the original address. 

B. Memory Repeater and Polling 

A dedicated CPU thread is created for each unique doorbell to monitor the first 64 bytes of its associated replacement page for changes. When a write is detected, the thread invokes a callback for event logging, and forwards the written value to the real NIC UAR. Figure 3 illustrates this mechanism. To keep CPU utilization low without increasing wake-up latency, we use monitorx /mwaitx (AMD) or umonitor /

umwait (Intel) for polling. These instructions block the thread until the cache line accessed by the GPU is invalidated. GPU doorbell writes traverse PCIe and are delivered as posted writes to the CPU’s coherence domain, invalidating the monitored cache line and waking the polling thread. Since mlx5 doorbell writes are exactly 8 bytes, each write invalidates a single cache line and wakes the polling thread, and no spurious wake-ups occur from unrelated memory traffic, as each fake page is dedicated to one doorbell and shared with no other data structure. Back-to-back doorbells that land before the polling thread wakes may coalesce into a single observation; this loses no information, because doorbell values carry a monotonically increasing producer index, so the latest observed value covers all preceding writes and WQE recovery (§V-C) accounts for the full producer-index delta. Parked polling threads do not contend with the application for CPU resources: while waiting in mwaitx /umwait , a core consumes no execution bandwidth and yields its resources to the sibling hyperthread. Since QPs have no core affinity, polling threads can additionally be pinned to any core, away from application threads. 

C. Doorbell and WQE Parsing 

Each mlx5 doorbell write encodes the target QP number and a producer index that identifies the position of the most recent WQE in the send queue. We extract these fields to associate doorbell events with the communication requests issued by the GPU. While the doorbell control sequence is written to (supposed) NIC memory that is readily accessible to CPU threads after interposition, the associated work queue elements and the data ranges they describe can reside in pure GPU memory. As such, individual WQEs are not directly readable on the CPU side at the time of the doorbell ring and require a device-to-host copy. Since doorbells happen frequently on latency-critical paths, we cannot synchronously copy and parse these structures on every doorbell write without a high performance penalty. Instead, we adopt a strategy where we split WQE recovery into a cheap per-doorbell step and a deferred batched parse step. On every doorbell, the polling thread records the timestamp and producer index, enqueues an asynchronous device-to-host copy of the newly posted WQE slots on a dedicated CUDA stream, and forwards the doorbell to the NIC. Because the copy does not need to be synchronous, forwarding is not delayed further. Parsing the recovered WQEs is deferred and done in batches: once a number of new WQE slots have accumulated since the last batch, the polling thread synchronizes the copy stream and parses the recovered entries before forwarding the current doorbell. These threshold-crossing doorbells are blocked on copy completion, while most doorbell writes are forwarded without deferral. This amortizes the synchronization and parsing costs across many doorbell writes while preserving accurate per-doorbell timing. This design is safe with respect to send queue wrap-around. Since the GPU can only overwrite a slot after the circular buffer wraps to avoid data corruption, batching at less than or equal to the number of available slots keeps us ahead of the wrap-around. We found a batch threshold of 128 to be safe for the workloads we tested, though, depending on the communication library configuration, it can be increased further. NVSHMEM’s IBGDA transport allocates 1024 WQE slots per send queue ( log_wq_size = 10) where a batch size of 512 can be used, and DeepEP similarly sizes its queues larger than its maximum number of in-flight requests to skip slot-availability checks. We note that corruption in WQE recovery is detectable by inspecting the monotonic producer index. Alternatively, batching can be tightened or disabled entirely to copy and parse every doorbell and its associated WQEs synchronously at the expense of a higher overhead. After each batch copy, we parse the relevant WQE control segments to recover the operation type ( opmod ), the number of data segments ( ds ), and the data segments themselves, which contain the remote address ( raddr ), remote memory key ( rkey ), and the byte count for each scatter/gather entry. By correlating deferred WQE metadata with previously recorded doorbell timestamps, S IGMA TRACE reconstructs fine-grained RDMA communication behavior: per-operation timing, per-QP traffic volume, and per-peer communication patterns for GPU kernels that are otherwise completely opaque to existing tools. 

Memory ordering considerations. A potential concern is whether WQE contents associated with doorbells are visible to the CPU when we copy them back. The correctness of GPU-initiated RDMA itself requires that all WQE stores reach the GPU’s coherence point before the doorbell write reaches the NIC. The NIC requires this ordering for its own DMA read of the WQEs following doorbell rings. Communication libraries therefore order WQE stores ahead of the doorbell store with a memory fence or a release store to ensure correct delivery; NVSHMEM, for example, issues a __threadfence 

or release-store ( st.release ) sequence when ringing the doorbell. This ordering is established on the GPU before the doorbell store is issued, and is thus independent of where that store lands. It holds for our replacement page identically as it does for the real UAR. The WQEs are read back after the doorbell is observed by the copy engine, which observes GPU memory at the same scope as the NIC’s DMA read. Once the polling thread observes a new doorbell value, every WQE slot covered by its producer index is already visible to our device-to-host copy, as it would have been to the NIC. VI. D. Case Study 1: Feature Showcase with Distributed BFS 

GPU-initiated communication can introduce communication and synchronization stalls that are hidden inside kernel execution and therefore invisible to many profiling tools. This limitation is particularly problematic for persistent kernels [9], and tightly coupled kernels that rely on device-side communication to make joint progress. Irregular applications exhibit this behavior: communication patterns in graph traversal depend on the evolving frontier and cannot be inferred from the host-side timeline. We demonstrate S IGMA TRACE ’s tracing and analysis capabilities on a distributed Breadth-First Search (BFS) implementation based on persistent NVSHMEM kernels across 4 GPUs, traced in Simple mode with doorbell collection enabled.

Checks for remote visited vertices generate additional atomic compare/swap operations, and remote frontier enqueues are done with memory puts and gets. Mycroft [18] and NCCL Inspector [19] are NCCL-specific tools that target activity at host-side proxy threads. Mycroft uses source code patching while NCCL Inspector makes use of the NCCL plugin API. Unlike S IGMA TRACE , neither tool can observe GPU-initiated operations, though they gather semantic NCCL data that may be obfuscated within lower-level traces we collect. NPKit [20] inserts compile-time macros into *CCL 

proxy threads and GPU kernel source code to emit timed events. It has broader support with NCCL and MSCCL, but requires recompilation of the target library with instrumentation macros enabled. Aegis [31] is a production fault diagnosis system for AI training infrastructure. It records RDMA work request metadata and per-collective timing to detect anomalies such as straggler ranks and network failures. Like Mycroft, it requires modifications to NCCL source code and does not observe GPU-initiated paths. Its focus is fault diagnosis rather than performance profiling. ucTrace [30] profiles UCX communication by instrumenting its transport (UCT) and protocol (UCP) layers, providing per-operation visibility into UCX endpoints, tagged messages, and RDMA operations. While ucTrace covers a broader set of transports than *CCL -specific tools, it operates at the UCX level, and does not see the underlying RDMA verbs or doorbell-level activity. OSU INAM [37] profiles MPI applications across the software stack, correlating MPI-level metrics with fabric-level counters in near real time. Like ucTrace, it observes host-side communication only and cannot attribute traffic to GPU-initiated operations. Nsight Systems [23] provides comprehensive traces of CUDA APIs, kernel launches, data transfers, collectives, and custom NVTX annotations. For network observability, it exposes system-level NIC throughput counters and Mellanox-specific congestion events. However, these views are aggregated across all processes sharing the NIC and cannot be attributed to individual GPUs, kernels, QPs, or remote endpoints. Nsight Systems also cannot observe GPU-side RDMA. On AMD systems, the ROCm Systems Profiler [24] samples OS-level NIC interface counters while ROCProfiler [38] provides API and kernel traces. Notably, ROCm Systems Profiler supports device-level RDMA transport counters on AMD’s own Pensando NICs, though neither tool offers per-operation or verbs-level visibility. Snoopie [21] is the tool closest in spirit to S IGMA TRACE as it tracks GPU-side memory operations using NVBit dynamic binary instrumentation [22]. It records every load and store in a kernel and classifies accesses as local or remote P2P. While Snoopie’s methodology can theoretically be extended to capture writes to UAR doorbells, instrumenting every memory instruction incurs overhead that is orders of magnitude higher than S IGMA TRACE ’s selective doorbell-level interposition. VIII. L IMITATIONS 

A. Hardware scope 

GPU-initiated RDMA tracing in S IGMA TRACE is currently only supported on NVIDIA GPUs with Mellanox NICs. This covers all GPU-initiated RDMA paths available on NVIDIA platforms. On AMD GPU systems, rocSHMEM [28] implements a similar GPU-initiated path over Mellanox NICs: its GPU-IB backend links against the same mlx5dv 

and libibverbs layers and implements IBGDA identically to NVSHMEM down to the send and completion queue configuration, memory layout, and WQE sizes. Its newer GDA backend likewise constructs WQEs and rings doorbells over PCIe from device code on the same NICs. The NIC-side interception therefore transfers directly to such systems, but the GPU-side instrumentation would need to be replaced with equivalent ROCm/HIP driver hooks. We note that the HIP host memory API is one-to-one with CUDA’s in both interface and semantics ( hipHostRegister and hipHostGetDevice Pointer are analogous to the calls we intercept). RCCL [29] does not currently support GPU-initiated RDMA and relies on CPU proxy threads, which are already visible to SIGMA TRACE ’s host-side instrumentation. Several other NIC architectures support GPU-initiated RDMA but are not yet covered by S IGMA TRACE : Broadcom Thor 2 [39], which uses a different driver stack, doorbell format, and WQE structure; and AMD Pensando Pollara 400 [40], a fully programmable RDMA NIC with a register interface unrelated to mlx5dv . While the GPU-NIC communication model is fundamentally similar (WQE construction in device memory followed by a PCIe doorbell write), and the interception mechanism itself is otherwise hardware-independent, the interposition layer would require per-NIC adaptations for the doorbell layout and WQE parsing. More notably, a GPU-initiated data path for AWS’s Elastic Fabric Adapter (EFA) shipped in NCCL 2.31 as the EFA GDA backend: CUDA kernels build 64-byte EFA send WQEs and ring the send-queue doorbell over the SRD transport with no host involvement [41], [42]. This path is closer to SIGMA TRACE ’s existing target than Thor 2 or Pollara 400—the 

libfabric EFA provider hands the application the send-queue and doorbell BAR addresses through its FI_EFA_ GDA_OPS extension [43], which the host plugin then makes GPU-visible with the cuMemHostRegister and cuMem HostGetDevicePointer calls that S IGMA TRACE already intercepts (§V-A). A port would need to hook libfabric 

or efadv in place of mlx5dv and decode the efa_io_tx_ wqe descriptors. We note that in EFA the transport rings a single 32-bit producer index with no separate doorbell record, which is simpler than the mlx5dv workflow. 

B. Software scope 

The driver interception and memory hijack techniques described in Section IV-B and Section V-A are CUDA-specific. We believe the methods are sufficiently general to adapt to other GPU software stacks: the core technique (replacing a device-visible memory mapping with a monitored proxy page) is independent of the vendor. An AMD port would require replacing cuGetExportTable interception with equivalent ROCm driver hooks and substituting the CUPTI-based GPU event correlation with its ROCm counterparts (ROCProfiler/rocTracer). Because ROCm is open source and mirrors the CUDA driver interfaces closely, we expect this port to be an engineering effort rather than a redesign, though we have not yet validated this path. 

C. Instrumentation scope 

We primarily use LD_PRELOAD to instrument communica-tion library functions, which is only compatible with libraries that expose symbols for dynamic linking. While the overhead is minimal, statically linked libraries and compiler-inlined function calls cannot be instrumented by symbol preloading. The libraries targeted in this work are designed to be dynamically loaded; however, we found that libcxi [44], the low-level interface for HPE Cray Slingshot systems, makes heavy use of 

static inline function definitions, which are invisible to our interposition layer. As a result, S IGMA TRACE cannot currently provide the same depth of tracing on HPE Cray systems as it does for 

libibverbs and mlx5 direct verbs, though we do provide partial observability through libfabric -level instrumentation. Full doorbell-level coverage and static-compilation support are porting tasks possible through dynamic instrumentation (Frida [45] or eBPF probes), which can reach inlined functions at the cost of higher per-call overhead. Combining LD_PRELOAD 

for supported libraries with dynamic probes for inlined calls is a viable direction for future work. IX. C ONCLUSION 

We presented S IGMA TRACE , a library-agnostic RDMA profiling framework that provides fine-grained observability into both CPU and GPU-initiated networking. By targeting the 

libibverbs and mlx5dv direct verbs layers—the common denominator beneath all InfiniBand and RoCE communica-tion libraries—S IGMA TRACE captures per-operation RDMA behavior without requiring source modifications, recompilation, or binary instrumentation with 1.3% overhead on NCCL AllReduce at 32 nodes. Our core contribution is the UAR memory interposition technique that replaces PCIe MMIO mapped memory pages with CPU-monitored proxy pages, enabling the first-ever observ-ability into GPU-initiated RDMA operations at overheads orders of magnitude below those reported for binary instrumentation [21]. We demonstrate that the interposition method adds 11.5% end-to-end overhead on a worst-case distributed BFS application while collecting previously invisible doorbell-level information that reveals hidden load imbalance and computation/commu-nication inefficiencies.
