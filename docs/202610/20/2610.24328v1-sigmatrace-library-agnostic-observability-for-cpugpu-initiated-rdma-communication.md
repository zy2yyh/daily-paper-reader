## 摘要
RDMA网络可在大型系统上实现低延迟、高带宽通信。然而，尽管其已被广泛采用，可观测性仍然不足。现有工具要么针对特定通信库，要么仅报告聚合数据，遗漏了逐操作行为。这一差距在GPU发起的网络通信中最为突出，因为其内核内RDMA操作对主机不可见。我们提出SigmaTrace，一个库无关的RDMA性能分析框架，为CPU和GPU发起的网络通信提供细粒度、逐操作的可观测性。它在libibverbs/mlx5dv层追踪操作，这是InfiniBand和RoCE上通信库之下的共同基础，并采用低开销的内存介入技术；据我们所知，该技术首次实现了无需修改源码或二进制插桩即可观测GPU发起的RDMA。主机侧追踪在128个GPU上的NCCL AllReduce中增加1.3%开销，在1024个GPU上的RCCL中增加不到2%。在持久内核BFS和专家混合（Mixture-of-Experts）推理中，SigmaTrace揭示了现有性能分析器无法看到的内核内屏障扩散以及2.13倍的节点间流量偏斜。

## Abstract
RDMA networking enables low-latency, high-bandwidth communication on large systems. Despite its adoption, however, observability is lacking. Existing tools target specific communication libraries or only report aggregated data, missing per-operation behavior. The gap is widest for GPU-initiated networking, whose in-kernel RDMA operations are invisible to the host.   We present SigmaTrace, a library-agnostic RDMA profiling framework providing fine-grained, per-operation visibility for CPU and GPU-initiated networking. It traces operations at the libibverbs/mlx5dv layers, the common denominator beneath communication libraries on InfiniBand and RoCE, and employs a low-overhead memory interposition technique that, to our knowledge, gives the first observability into GPU-initiated RDMA without source patching or binary instrumentation.   Host-side tracing adds 1.3% overhead on NCCL AllReduce at 128 GPUs and under 2% on RCCL at 1024 GPUs. On a persistent-kernel BFS and Mixture-of-Experts inference, SigmaTrace exposes an in-kernel barrier spread and 2.13x inter-node traffic skew invisible to existing profilers.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：大规模 AI 训练/推理与科学计算高度依赖 RDMA 网络（NCCL、NVSHMEM、MPI、UCX 等）。随着 GPUDirect RDMA 与 GPUDirect Async（IBGDA）的引入，控制路径也被下沉到 GPU：GPU 线程在显存中构造 WQE、通过 PCIe 写 NIC 门铃（doorbell/UAR）、轮询 CQE，全程绕过 CPU。DeepEP、NCCL GDAKI、rocSHMEM 等已采用该范式。
- **核心痛点**：可观测性严重滞后。
  - 现有工具（Mycroft、NCCL Inspector、NPKit、ucTrace、Aegis）只插桩主机侧代理线程或特定库 API，在 kernel launch 处即“止步”，完全看不到内核内 RDMA。
  - 二进制插桩类工具（Snoopie + NVBit）需逐条插桩所有内存指令，开销高出数量级。
  - 厂商分析器（Nsight Systems、ROCm Systems Profiler）只提供**跨进程聚合**的 NIC 计数器，无法归因到单个 kernel / GPU / QP / 远端节点。
- **本质矛盾**：GPU 发起的 RDMA 被“降解”为普通内存读写（`STG.E.STRONG.SYS` 等），没有 API 边界或软件事件可作为观测点——**最关键的通信操作反而最不可见**。
- **论文主张**：无论软件层如何绕过，GPU 与 NIC 之间的硬件接口不可绕过——每个 RDMA 操作最终都是一次对 NIC 门铃（PCIe BAR 映射的 MMIO）的写。该点位于所有通信库之下，是唯一统一的观测锚点。

## 2. 方法论

### 2.1 核心思想
在 **libibverbs / mlx5dv** 层（InfiniBand/RoCE 上所有通信库的公共分母）进行插桩，并用 **UAR 内存介入（Memory Hijack-and-Repeat）** 技术，将映射到 GPU 地址空间的 NIC 门铃页替换为 CPU 固定内存页，从而在不改源码、不做二进制插桩的前提下截获 GPU 发起的门铃写。

### 2.2 系统架构（Profiler + Correlator 两段式）
- **Profiler（热路径）**：LD_PRELOAD shim 形式的事件提供者，按需选择性启用；每线程写入私有 ring buffer，**不做同步/通信**，最小化开销。
- **Correlator（离线）**：并行读取原始事件、合并事件流、归一化时间戳、重建 QP 拓扑、关联 doorbell 与 WQE。

### 2.3 主机侧拦截
- 三种符号解析路径均支持：链接时绑定、`dlopen/dlsym/dlvsym` 运行时解析、内部对象符号表（高频分发表）。
- **CUDA 驱动拦截**：LD_PRELOAD 对 CUDA 无效，改为拦截 `cuGetProcAddress` 与 `cuGetExportTable` 暴露的**内部派发表**，保存原函数指针并替换为 wrapper。

### 2.4 UAR 内存介入（核心创新）
识别并劫持 GPU 发起网络的**三步建立序列**：
1. `mlx5dv_devx_alloc_uar`：分配 UAR，得到 PCIe BAR 映射的 doorbell 地址；
2. `cuMemHostRegister`：将 MMIO 区间注册为 CUDA 可访问；
3. `cuMemHostGetDevicePointer`：取得 GPU 侧指针。

在步骤 3 处，分配一个**4KB 固定主机内存假页**并返回其设备侧指针。由于 GPU 对固定主机内存与对 UAR 的写都是**非缓存 posted write**，语义完全等价，应用无感知。

### 2.5 轮询与转发（Repeater）
- 每个 doorbell 一个专用 CPU 线程，监视假页前 64 字节。
- 使用 `monitorx/mwaitx`（AMD）或 `umonitor/umwait`（Intel）**休眠轮询**：等待 GPU 写使缓存行失效后唤醒，几乎不占执行带宽，可绑定到任意核。
- mlx5 doorbell 为 8 字节、独占缓存行，无虚假唤醒；连续 doorbell 合并不会丢信息（生产者索引单调递增，取最新值 + 索引差即可恢复全部）。

### 2.6 WQE 恢复（延迟批处理）
- 门铃只携带 QP 号 + 生产者索引；WQE 位于纯 GPU 内存，需 D2H 拷贝。
- **每 doorbell**：记录时间戳与生产者索引、在专用 CUDA stream 上异步发起新 WQE 槽位的 D2H 拷贝、**立即转发门铃**（不阻塞）。
- **批量解析**：累积到阈值（默认 128 槽；IBGDA 1024 槽可用 512）后再同步 stream 并批量解析，摊销同步与解析成本。
- **安全性**：批大小 ≤ 可用槽数即可跑在环形缓冲回绕之前；解析 `opmod`、`ds`、`raddr`、`rkey`、字节数。
- **内存序论证**：GPU 发起 RDMA 本身要求 WQE 存储在门铃写之前到达一致性点（fence/release store），该序与门铃落到哪个地址无关；拷贝引擎与 NIC DMA 处于同一观察域，故观察到的门铃保证其覆盖的 WQE 已可见。

### 2.7 事后关联与输出
- **时间戳归一化**：RDTSC 周期计数 + 初始化时 PTP 同步的墙钟对，转纳秒。
- **QP 拓扑重建**：由 `mlx5dv_devx_umem_reg`（含 `cudaPointerGetAttributes` 判断显存/主机内存）、`MLX5_CMD_OP_CREATE_QP` 邮箱解析出 SQ 地址/容量/偏移、服务类型、QP 号。
- **doorbell→WQE 关联**：按 QP 号 + 生产者状态匹配，标注操作类型、远端地址、传输大小。
- **导出**：Perfetto Protobuf（跨节点 flow arrow + 自定义 doorbell track）、PerfettoSQL 查询；Aggregate 模式输出 JSON 通信矩阵。

### 2.8 三种追踪模式
| 模式 | 内容 | 开销定位 |
|---|---|---|
| Aggregate | 仅源/目的通信量，线程本地聚合，无时间戳 | 最低 |
| Simple（默认） | 时间戳事件，**省略** `ibv_poll_cq` 等高频操作 | 低 |
| Full | 全部事件，含逐 WR、逐 CQE | 最高，用于短时定向调试 |

未启用的事件**完全关闭采集**，不产生任何开销。
